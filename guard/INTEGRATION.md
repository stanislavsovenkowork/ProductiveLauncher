## Подписи и граница доверия

`guardRelease` подписывается Gradle из существующего корневого `keystore.properties`, тем же ключом, что основной release. Значения секретов не выводятся. `guardDebug` использует обычный Android debug-ключ, соответствующий QA-приложению на этой машине. Проверить публичные SHA-256 сертификатов обоих APK перед установкой.

Release Guard разрешает **только** `dev.stanislav.focusdeck`; debug Guard — **только** `dev.stanislav.focusdeck.qa`. Перед выдачей allowlist, после её применения и при проверке активного статуса Guard вызывает `PackageManager.checkSignatures()` для себя и выбранного установленного лаунчера. Несовпадение или отсутствие пакета блокирует активацию. QA никогда не разрешается release-сборкой. Debug Guard не доверяет production-пакету автоматически.

Канала управления политиками от лаунчера к Guard **нет**. Нет общего токена, незащищённого receiver, публичного для обычных приложений `unlock` или передачи результата ритуала. Receiver политик требует системное разрешение `android.permission.DUMP` и понимает ACTIVATE, STATUS, RECOVER; это путь авторизованного ADB/привилегированного администратора, а не API лаунчера. Отдельно добавлен узкий `scheduleWake(epochMillis, reason)`, защищённый signature permission, проверкой реального UID нужного лаунчера и подписи. Он не может менять политики. Полный контракт, код вызова и ограничения — в `SCHEDULING.md`.

## 1. Активация

1. Main отдельно устанавливает нужную пару подписанных приложений, проверяет независимое восстановление, затем **осознанно** выполняет допустимый provisioning. Guard сам owner не назначает. Персональные аккаунты не удалять, setup-флаги не менять.
2. В Guard пользователь нажимает «Activate policy…», подтверждает предупреждение и проходит системное подтверждение device credential. Для уже авторизованного ADB-теста вместо диалога можно явно отправить ACTIVATE; дополнительные параметры отсутствуют и extras игнорируются. Наличие настроенного device credential по-прежнему проверяется, но вводить его на каждом ADB-вызове не требуется.
3. Guard проверяет, что неявный MAIN/HOME разрешается в точную MainActivity нужного варианта в этом Android-пользователе. Другой Home/chooser/отсутствие — понятный отказ до записи журнала; Home автоматически не меняется. Проверка повторяется во время и в конце активации. Далее проверяются owner/full-user profile-owner, подпись выбранного лаунчера, отсутствие активного Lock Task/pinning и стандартную исходную политику. Сохраняет журнал до первого изменения.
4. Guard задаёт выбранный пакет и маску 112, проверяет чтением результат и сохраняет ACTIVE. Затем включает ежедневный alarm на следующие локальные 23:00. При ошибке регистрации пытается откатить свою политику. DORMANT-состояние не активируется обновлением или STATUS; прежний тестовый user10 удалён.
5. Guard **не запускает** Lock Task. Когда основной движок установит обязательность ритуала, возобновлённая и разблокированная Activity лаунчера проверяет `isLockTaskPermitted(packageName)` и вызывает `startLockTask()`.
6. После вызова лаунчер заново читает `ActivityManager.lockTaskModeState`. Только LOCKED означает управляемый режим; PINNED — снимаемое закрепление. Политика может измениться между проверкой и стартом.

```sh
# Только main после проверки rollback; USER_ID — пользователь с owner Guard.
adb -s 62051JEA324712 shell am broadcast --user USER_ID \
  --receiver-foreground --include-stopped-packages \
  -n dev.stanislav.focusdeck.guard/.AdbRecoveryReceiver \
  -a dev.stanislav.focusdeck.guard.ACTIVATE
```

Ожидаем `result=0`, ACTIVE и проверенную маску 112/нужный пакет. Код 1 — состояние не проверено либо требуется recovery, код 2 — отказ/неподдерживаемая операция. Имя action только полное, с namespace. Изменять baseline, allowlist, маску или подпись через аргументы невозможно. Повторная ACTIVATE при активной/незавершённой транзакции отказывает, сохраняя первоначальный снимок.

## 2. Статус

- Лаунчер читает штатные API `isLockTaskPermitted(packageName)` и `lockTaskModeState` в своём процессе. `true` в первом API не означает, что task уже заблокирован, и не раскрывает маску системных панелей.
- Экран Guard и защищённая ADB-команда STATUS читают журнал и текущую resolved policy. ACTIVE означает совпадение политики и подписи, а не доказательство закрытой шторки на устройстве.
- При NEEDS_RECOVERY/UNVERIFIED не изображать успешное ограничение. Нужна проверка/восстановление. Никакого автоматического повторного наложения политики по status-запросу или callback нет.

## 3. Успешный ритуал

1. Основной процесс сохраняет данные, повторно проверяет реальные требования и надёжно записывает завершение. Ошибка vault не считается успехом.
2. Лаунчер переводит required в false и вызывает `stopLockTask()` для сессии/task, который начал сам. Затем проверяет фактический режим. Исключение/оставшийся LOCKED нельзя показывать как снятие ограничения.
3. Allowlist Guard при обычном успешном завершении **остаётся** настроенным для следующего ритуала. Команда RECOVER не является обычным «ритуал завершён»: она административно разоружает Guard до новой явной активации.
4. После перезапуска процесса нельзя восстанавливать право снять чужую сессию из одного vault-маркера или глобального LOCKED. Если принадлежность сессии не доказана, независимый recovery снимает политику. Нормальное восстановление launcher-owned task после process death требует отдельного теста основной Activity.

## 4. Независимое аварийное восстановление

Запускается отдельный процесс `dev.stanislav.focusdeck.guard`; лаунчер, его Binder, vault и результат ритуала не используются. Receiver direct-boot-aware, журнал — в device-protected storage. При испорченном журнале Guard всё равно пытается удалить **свой** вклад в Lock Task, но не заявляет проверенный откат без исходного снимка.

RECOVER сначала отключает расписание и отменяет ежедневный/одноразовый alarm. Если отмену нельзя подтвердить, политика всё равно снимается, но полного успеха нет. Каждый оставшийся callback дополнительно проверяет настоящий ACTIVE-статус перед любым запуском.

```sh
# Выполняет main только после подготовки rollback; USER_ID — пользователь с owner Guard.
adb -s 62051JEA324712 shell am broadcast --user USER_ID \
  --receiver-foreground --include-stopped-packages \
  -n dev.stanislav.focusdeck.guard/.AdbRecoveryReceiver \
  -a dev.stanislav.focusdeck.guard.RECOVER
```

Ожидаем `result=0`, текст RESTORED, затем отдельно проверяем режим task. Если сам Guard не может запуститься, запасной путь — `dpm remove-active-admin --user USER_ID dev.stanislav.focusdeck.guard/.GuardAdminReceiver` благодаря testOnly=true. Для нормального восстановления сначала используется RECOVER, чтобы сравнить исходную политику; удаление admin шире и отменяет enrollment.

Этот агент не устанавливал APK и не выполнял provisioning, активацию либо recovery на телефоне. Проверки реальной блокировки, полномочий стороннего UID, смерти процессов, emergency и восстановления остаются за main.

## Проверка Home в Main

Host может сам читать `RoleManager.isRoleHeld(RoleManager.ROLE_HOME)` (публичный API с Android 10) и дополнительно проверять точный компонент через `PackageManager.resolveActivity(Intent(ACTION_MAIN).addCategory(CATEGORY_HOME), MATCH_DEFAULT_ONLY)`, без `setPackage`. Для полного разрешения HOME-кандидатов добавить соответствующий `<queries><intent>` в Main. Проверять на resume/focus и перед новым startLockTask, а не делать polling. Это отдельная проверка от rootPackage/task ownership: совпадение rootPackage не доказывает default Home или тип HOME текущего task.

При drift показывать потерю проверенной конфигурации; не создавать новую managed-сессию и не считать текущую защиту полной. Не стирать сохранённый ownership и не снимать уже существующий lock автоматически только из-за drift; штатное завершение принадлежащей Main сессии и независимый RECOVER должны сохраняться. Guard STATUS предназначен для DUMP-отправителей; нового обычного app status/policy канала нет. Установка QA Home остаётся отдельным осознанным действием main.

SCHEDULE_WAKE теперь отказывает **до расходования лимита**, если уже известно об отсутствии owner BAL или exact-alarm access. DAILY может работать в прежнем ограниченном режиме. Возврат после принятого запроса всё ещё не гарантируется: последующая смена политики/разрешений/keyguard и смерть Main между сообщениями не атомарны. Main должен сохранять исходный epoch+reason до отправки и использовать их для идемпотентного повтора, не продлевать deadline после таймаута.
