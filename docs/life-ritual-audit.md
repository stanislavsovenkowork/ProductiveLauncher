Воспроизведения ниже — сценарии для main-агента, а не заявления об уже наблюдавшихся сбоях на Pixel. Политика системного Guard/Lock Task вне области аудита.

Проверены RitualViewModel/Engine, RootScreen, NutritionViewModel/Screen/Repository, связанные операции VaultDayStore, MainActivity и существующие тесты ритуалов. Номера строк относятся к текущему рабочему дереву, не только к HEAD `2007e7a74bf8d42c67aa19cd6d83140ffd98b944`.

## Приоритеты

| ID | Приоритет | Дефект | Условие |
|---|---|---|---|
| R1 | P1 | Завершённый ритуал не пересчитывается после удаления обязательных данных внутри App | Без смены Activity/окна ритуала |

## R1 — P1: нет инвалидации готовности при изменении данных

**Место:** `ui/ritual/RitualViewModel.kt:131–143,217–260`; `ui/root/RootScreen.kt:217–275`; `ui/nutrition/NutritionViewModel.kt:135–149`.

RitualViewModel получает разовые снимки заметок и `observeMealsForDay(...).first()`. Подписок на изменения заметок/еды нет. Его 30-секундный цикл проверяет смену окна и окончание emergency, а не содержимое. Обычный возврат из питания/дневника лишь закрывает overlay; обновление ритуала есть только в ветке уже видимого ритуала. Поэтому сохранённое в `_uiState` `mandatory=false` продолжает открывать вкладки после нарушения требований.

**Воспроизведение:**
1. В день после активации закончить утренний ритуал с валидным планом и дневником; emergency не использовать.
2. Не выходя из Activity, в обычном Плане удалить/убрать время у блоков так, чтобы осталось меньше 540 минут, либо удалить главный блок. Переключиться на Главную/Приложения; подождать более 30 секунд.
3. Отдельно повторить с очисткой утреннего дневника; для завершённого вечера — удалить последний приём пищи или изменить подтверждённую запись через обычное Питание.
4. Ожидается повторная проверка обязательных условий; по текущим связям данных вкладки остаются доступны. После `onResume`/перезапуска проверка возвращается (`MainActivity.kt:149–179`).

**Исправление:** инвалидировать ритуал по завершённым изменениям соответствующих дат и еды, либо собирать реактивный снимок. Не полагаться на выход из Activity. Учитывать, что вечер читает две даты: подписки только на текущую выбранную заметку недостаточно. Публиковать загрузку/проверку без краткого открытия вкладок. Минимальный регрессионный тест: завершить → изменить каждый источник → дождаться подтверждённой записи → получить `mandatory=true` без lifecycle-события.

## R2 — P1: финализация может стереть более свежий ввод

**Место:** `RitualViewModel.kt:273–287,325–360`; `ui/ritual/RitualScreen.kt:223,389`.

`finish(journalText, ifThenText)` работает с захваченными строками. После нескольких suspend-операций он без проверки версии удаляет оба draft-ключа. `updateJournalDraft`/`updateIfThenDraft` не берут `actionLock`; поля и вкладки экрана остаются редактируемыми при `busy=true`. Новый ввод B может попасть в prefs после захвата A, а завершение A затем удалит B. Коллектор B позже увидит отсутствие соответствующего ключа и пропустит запись.

**Воспроизведение:** подготовить все условия; замедлить/приостановить запись маркера завершения в тестовом хранилище. Нажать «Завершить день» с текстом A. Пока `busy=true`, перейти на вкладку дневника и дописать отличимый хвост B (или изменить «Если отвлекусь…» на плане). Разрешить I/O. Проверить vault, prefs и повторное открытие: B не должен исчезать. Для детерминированного VM-теста ставить барьер непосредственно перед возвратом записи маркера, чтобы поздний ввод точно оказался перед удалением ключей.

**Исправление:** version/generation для каждого `(window, field)`; финализация сохраняет конкретную версию и удаляет только её при совпадении. Если появилась новая версия, сохранить её и заново проверить готовность перед закрытием либо оставить экран открытым. Блокировка полей на время finish — дополнительная UI-защита, но не замена согласованию версий. Не заменять потерю ввода молчаливым отказом принимать изменения.

## R3 — P1: публикация старого окна после смены фазы

**Место:** `RitualViewModel.kt:217–225,237–260`; `RitualEngine.kt:48–57`; `RootScreen.kt:110–115,150,280`.

В начале `refreshNow()` фиксируется `window`. После чтения файлов/БД обязательность считается с **новым** `ritualWindow(clockNow())`. Если чтение пересекло границу, `shown != actual`, поэтому `shouldRequireRitual` возвращает false независимо от требований нового окна. Одновременно публикуется `loading=false`; при `preview=false` Root показывает обычные вкладки. Повторный опрос обычно исправит это при следующем 30-секундном тике, но до него появляется реальный промежуток без обязательного экрана.

**Воспроизведение:** без focus-grace/emergency, после дня активации начать refresh в 22:59:59 и задержать чтение до 23:00:01. Вечер не завершён. Проверить последовательность состояний: не должно появляться `loading=false, mandatory=false` для старого окна. Повторить 05:59:59 → 06:00:01. Использовать управляемые часы и барьер I/O; просто перевод времени после полностью законченного refresh проверяет другой случай.

**Исправление:** перед публикацией сверять ключ окна/поколение запроса с текущими; устаревший снимок отбрасывать и перечитывать, сохраняя безопасное состояние проверки. Аналогично повторить проверку окна **после** получения `actionLock`: сейчас `change()` проверяет дату до ожидания мьютекса, затем берёт уже новое `_uiState.window` для старого нажатия. Не переносить аргументы старого действия на новую дату.

## R4 — P2: draft восстановлен в UI, но autosave не возобновлён

**Место:** `RitualViewModel.kt:79–95,115–126,150–171,217–252`.

Долговечное наличие draft в prefs само по себе не вызывает запись. После запуска `refreshNow()` показывает значение из prefs, а новые SharedFlow начинают без прежних событий. Отправка происходит только из `update*Draft`. Если больше не печатать, восстановленный текст не попадёт в vault ни через секунду, ни через минуту. После перехода к другому окну старый draft остаётся под старым ключом и больше не виден на текущем экране. Это **осиротевшая очередь**, а не доказанное физическое удаление prefs.

**Воспроизведение:** остановить процесс после того, как draft A уже оказался на диске prefs, но до vault-write (окно debounce либо заблокированное I/O). Запустить снова, убедиться, что A виден, ничего не печатать, ждать 5+ секунд. Проверить, что vault остаётся старым. Затем пройти 06:00: UI переключится на другой draft-ключ, а A всё ещё не перенесён в файл. Вторая проверка: события разных окон подряд в интервале debounce — единый поток может вытеснить запись предыдущего окна.

**Связь с persisted completion:** если файл уже содержит валидную запись и маркер завершения, а durable draft — её ещё не записанное сокращение/удаление, restart может оставить gate открытым: `progress` считается по файлу, тогда как `journal` берётся из prefs. Проверить этот подслучай отдельно. Это следствие невосстановленной pending-записи, а не обход чистой `ritualProgress` одним маркером.

**Исправление:** хранить и повторно поднимать очередь pending-записей по `(window, field, version)`, в том числе для прошлых окон; не только текущий UI-draft. На смене окна не отбрасывать старую работу. Повторная отправка должна учитывать изменившийся внешний документ/конфликт, а не безусловно затирать поле старым локальным текстом. Удалять запись очереди только после подтверждённой записи той же версии. Проверить сценарий с недоступным vault и последующим восстановлением доступа.

## R5 — P2: hard kill до завершения записи preferences

**Место:** `RitualViewModel.kt:160–171`; для флага использованного emergency тот же механизм в `364–382`.

`androidx.core.content.edit { ... }` по умолчанию вызывает `apply()`. Это сразу изменяет память процесса, но запись на диск асинхронна. UI принимает текст без подтверждения её завершения; затем начинается отдельный секундный debounce записи в vault. Обрыв процесса до обоих сохранений может потерять хвост. Это установленное окно отсутствия гарантии, **не измеренный на Pixel факт потери при каждом force-stop**. [Android KTX](https://developer.android.com/kotlin/ktx), [SharedPreferences.Editor.apply](https://developer.android.com/reference/android/content/SharedPreferences.Editor#apply()).

**Воспроизведение:** вводить уникальные возрастающие суффиксы; обрывать foreground-процесс до завершения async-disk-write, затем сравнивать восстановленную строку с последним принятым вводом. Нужна серия таймингов либо контролируемая задержка сохранения. Отдельный тест после подтверждённой durable-записи должен сохранять текст. Штатный уход в фон не эквивалентен hard kill: framework дожидается pending-записей на lifecycle-переходах; нельзя объявлять обычный Back/rotation воспроизведением этой гонки. [Контракт apply](https://developer.android.com/reference/android/content/SharedPreferences.Editor#apply()).

**Исправление:** определить durable-checkpoint, сериализовать локальные версии в атомарном хранилище с подтверждаемым результатом и восстанавливаемой очередью; отражать ещё не сохранённый ввод отдельно от подтверждённого. Асинхронный writer сам по себе не гарантирует каждый символ до мгновенного kill. Не ставить `commit=true` на UI-поток для каждого нажатия: это переносит диск в ввод. Для emergency записать использованную квоту и срок до предоставления доступа; контроль ошибки/подтверждения относится к интеграции с Guard и здесь не менялся.

## R6 — P2: пауза в наборе меняет содержимое поля

**Место:** `RitualViewModel.kt:100–109,228–242`; `DailyNoteParser.kt:121–137,405–411`; для if-then — `RitualEngine.kt:219–222`.

Autosave пишет `value.trim()`, удаляет draft и вызывает refresh. Поле затем получает нормализованный текст из файла. Поэтому конечный пробел или пустая строка исчезает из **редактируемой** строки после паузы. Поле if-then дополнительно теряет внутренние переводы строк через `RitualNotes.put`.

**Воспроизведение:** в дневнике ввести `Сегодня ` с конечным пробелом, подождать запись, затем напечатать следующее слово. После refresh пробел уже удалён, слова могут склеиться. Повторить `Первая мысль\n\n`, пауза, следующий абзац. Проверить if-then с двумя строками. Важно ждать успешный autosave, а не только таймер при недоступном vault.

**Исправление:** не подменять активный editor buffer сериализованной копией при подтверждении собственной записи. Хранить редактируемую строку/selection отдельно от нормализованного представления и версии, записанной в файл. Формат if-then либо должен сохранять многострочность, либо UI должен явно соответствовать однострочному контракту; молчаливое схлопывание после паузы недопустимо.

## R7 — P2: доступный выбор даты ломает ritual planner

**Место:** `RootScreen.kt:170–188,195–197`; `ui/planning/PlanningScreen.kt:58–70`; `PlanningViewModel.kt:155–163`.

Root показывает PlanningScreen только при равенстве выбранной даты и даты ритуала, но сам PlanningScreen разрешает выбрать другую дату. После её выбора компонент заменяется на «Открываю план…», а повторного выбора даты ритуала в этой ветке нет.

**Воспроизведение:** обязательный ритуал → «Открыть расписание» → открыть выбор дней → выбрать другую дату. Надпись остаётся после окончания I/O. «К ритуалу» и повторный вход восстанавливают экран; это не обход gate, но ложная бесконечная загрузка.

**Исправление:** в ritual-контексте фиксировать/ограничивать выбор даты или обрабатывать его явно, сохраняя рабочий экран и понятный возврат. Не изображать загрузку, которую никто не выполняет. Проверить также смену окна в 23:00 при уже открытом planner.

## R8 — P2: форма питания не имеет сохраняемого черновика

**Место:** `NutritionScreen.kt:76–98,289–299`; `NutritionViewModel.kt:121–149`.

Название, калории и тип формы живут в `remember`; до «Добавить/Сохранить» они не переданы VM/БД. Фактическое пересоздание Activity/композиции или уход из overlay удаляет их. При возвращении `LaunchedEffect(editingMealId)` заново заполняет форму старой записью либо очищает её. Для утреннего/вечернего ритуала это потеря ещё не подтверждённого пользовательского ввода, не обход проверки еды. В `AndroidManifest.xml:36` заданы `configChanges` для orientation/screenSize: обычный поворот здесь не обязан пересоздавать Activity и сам по себе не является воспроизведением.

**Воспроизведение:** из ритуала открыть питание, ввести название и калории, не нажимать «Добавить», вернуться к ритуалу и снова открыть питание. Отдельно проверить фактическое пересоздание Activity. Повторить с несохранённой правкой существующей еды. Ожидается сохранённый draft либо явное предупреждение о потере; сейчас данные сбрасываются. Отдельно не считать показанную пустую форму после нажатия «Добавить» доказательством успешной записи: UI очищается до окончания coroutine/Room-вставки.

**Исправление:** draft в VM/SavedStateHandle или сохранённом состоянии маршрута с ключом `(date, editingMealId)`; при необходимости стойкости к hard kill — тот же durable-store, что в R5. Инициализировать из Meal только для нового контекста редактирования, не поверх восстановленного черновика. Очищать форму после результата операции; ошибки записи показывать, не теряя введённое.

## Проверенные защиты и границы выводов

- **Пустое питание не подтверждается:** VM отбрасывает пустой список, неподходящие названия и отрицательные калории (`RitualViewModel.kt:308–317`). DAO выбирает записи по дате, а `foodReady` ещё проверяет дату каждой записи. Нулевые калории разрешены условиями владельца; это не дефект.
- **Подтверждение привязано к содержимому:** fingerprint включает ID, дату, тип, название и калории (`RitualEngine.kt:141–152`). Изменённые/удалённые записи при свежем расчёте становятся неготовыми. Дефект R1 — отсутствие самого свежего расчёта в обычной навигации.
- **Маркер завершения сам по себе не обходит требования:** `ritualProgress` требует маркер вместе с дневником, планом и едой (`165–176`). Cold start заново читает файлы/БД; pending-draft оговорён в R4. Не найден постоянный bypass только за счёт сохранённого `…: да` при невалидных данных.
- **Прямой выход из активного mandatory через overlays не найден:** Root допускает только питание/vault/план, скрывает вкладки; Back возвращает к ритуалу и обновляет состояние (`RootScreen.kt:134–145,150–216,280–282`). Life/Apps не маршрутизируются этой веткой. Emergency и focus-grace — отдельные явно заданные разрешения, не баг сами по себе.
- **Удаление задачи/дневника движок обрабатывает:** объём плана, наличие приоритета и journal readiness вычисляются по актуальным заметкам. Старый UI-снимок и старое action-окно — отдельные проблемы R1/R3.
- Прочитаны `RitualRequirementsTest.foodRequiresEntriesAndConfirmationOfExactContents`, `completionCannotBeForgedWithMarkerAndSingleDot`, `RitualEngineTest.completionMarkerCannotBypassMissingRequirements` и `RitualFlowTest`. Они проверяют чистые функции/парсер; наличие этих тестов не подтверждает lifecycle, async preferences, VM interleaving или навигацию. В этом аудите они не запускались.
