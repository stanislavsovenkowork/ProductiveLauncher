# FocusDeck: проверка реализации жизненной системы

> Исторический обзор. При публикации абсолютные локальные ссылки заменены ссылками на исходники репозитория; номера строк относятся к условиям этого обзора. Текущее описание функций — в [functional/README.md](functional/README.md).

29 сентября 2026. Статический обзор текущих `LifeEntry`, `LifeNoteCodec`, `LifeRepository`, `LifeViewModel`, тестов codec и `life-system-ux.md`. Научная база — уже подготовленный [отчёт](life-system-evidence.md), без нового поиска и новых метаанализов. Изменён только этот документ; код, тесты и vault не менялись. Приведённые ниже сценарии **ещё не выполнены** на приложении.

**Вывод:** модель поддерживает полезный минимальный цикл, но до заявления о сохранности истории решений нужно исправить её запись и проверку после слияния. Далее — отделить перенос проверки от состоявшегося обзора, убрать автоматические обязательства из черновиков и сделать явным переход от вывода к следующему действию. Добавление новых полей менее важно, чем корректность этих переходов.

Код развивается параллельно. Снимок прочитан около 00:18–00:20 Minsk. SHA-256, первые 12 символов: `LifeEntry d3ca8e53b6a7`, `LifeNoteCodec d3d020a8cd86`, `LifeRepository 8b89df898883`, `LifeViewModel 84163c57f7ff`, UX `8089a0559350`. На момент проверки `ui/life` содержал только ViewModel; фактический новый экран и его доступность не проверены. Ниже различаются подтверждённая логика кода и риски проектируемого интерфейса.

## Что уже согласовано с доказательствами

- Родительские связи необязательны; UX разрешает задачу и проект без полной классификации. Иерархия представлена как организация данных, не доказанный метод управления жизнью.
- Ожидание и результат решения разделены; принятие требует ожидания и даты проверки. У цели есть личная причина и критерий результата; выполнение задач не объявлено автоматическим достижением цели.
- Обзор допускает короткий ответ и сохранение текущего режима. Новых квот слов в модели обзора нет.
- Codec обнаруживает конфликт одного поля, сохраняет независимые внешние правки и учитывает ограждённые блоки кода. Это полезные защиты, но они не обеспечивают логическую согласованность истории решения целиком.

Это соответствие принципам из evidence, а не подтверждение эффективности FocusDeck. Утверждений о клиническом эффекте и рекомендаций клинических вмешательств не добавлять.

## Риски, которые следует исправлять первыми

Приоритет **P1** означает важную ошибку данных или смысла до выпуска соответствующего сценария. **P2** — ограничение/продуктовый риск: допустим упрощённый вариант с честным описанием. Признаков безусловного P0 для всей системы этот обзор не устанавливает.

### R1 · P1 · История записывает не ту версию результата

**Факт кода:** [LifeRepository.prepare](../app/src/main/java/dev/stanislav/focusdeck/data/life/LifeRepository.kt#L180) вычисляет `changedChoice` и `reviewed` независимо, но выбирает один тип события. При обоих `true` источник — `base`, а поля для записи — `OUTCOME/LESSON`. Поэтому при одновременной смене ожидания и добавлении результата в историю попадёт **предыдущий** результат, возможно пустой. Новый результат остаётся в текущем поле, но не получает корректной исторической записи и может исчезнуть из видимой истории при последующей замене.

Другие ветки той же проблемы:

- Первое принятие с уже заполненным результатом выбирает событие проверки; первоначальный выбор и ожидание не фиксируются отдельным снимком.
- Изменение только `CRITERIA`, `OPTIONS`, `COST` или `LESSON` не запускает запись события. Начальный снимок вообще не включает `COST` и дату проверки.
- Принятая извне запись без `decided_on` не проходит условие `changedChoice`; отсутствие исходных ожиданий нельзя выдавать за наличие достоверной истории.

**Значение:** журнал должен позволять сравнивать то, что было известно до результата, с фактом после него. Иначе интерфейс поддерживает переписывание ожиданий задним числом, хотя показывает «Историю».

**Минимальное исправление:** разделить «Принять», «Записать результат» и «Изменить решение» на явные события, хотя бы внутри одного сохранения. Каждое хранит соответствующую версию выбора, ожидания, критериев, срока проверки и результат; новая версия ссылается на предыдущую. Сохранение обычной формы не должно само считаться новым принятием. Позднее внесённую запись обозначать отдельно. Markdown-истории достаточно; новая база событий для этой итерации не требуется.

Не обещать неизменяемость файла в Obsidian. Обещание продукта уже: приложение сохраняет версии при собственных операциях и сообщает, когда происхождение внешних правок неизвестно.

### R2 · P1 · Корректность проверяется до слияния, а сохраняется другой документ

**Факт кода:** [save](../app/src/main/java/dev/stanislav/focusdeck/data/life/LifeRepository.kt#L102) вызывает `prepare` и проверяет активацию **до** чтения свежей заметки; [merge](../app/src/main/java/dev/stanislav/focusdeck/data/life/LifeNoteCodec.kt#L80) объединяет независимо изменённые поля. После слияния итоговые обязательные поля и связь события с ожиданием повторно не проверяются.

Пример: принятая запись открыта на телефоне; в Obsidian очищают ожидание, а на телефоне меняют только название. Локальная проверка видит старое непустое ожидание; merge сохраняет внешнее пустое значение вместе с новым названием. В другом случае внешний новый прогноз и локальный результат объединяются без выяснения, к какой версии прогноза относится результат.

**Минимальное исправление:** проверить итоговую модель до записи. Для принятия/пересмотра ожидания, выбор, критерии и история образуют связанные данные: при внешнем изменении предложить перечитать их либо консервативно остановить операцию. Независимые пользовательские секции можно продолжать сливать. Проверка совпадения записанных байтов сама по себе этого не решает.

### R3 · P1 · Вложенный заголовок может потерять часть черновика

**Факт кода:** [codec.create](../app/src/main/java/dev/stanislav/focusdeck/data/life/LifeNoteCodec.kt#L63) вставляет текст поля как Markdown; [sections](../app/src/main/java/dev/stanislav/focusdeck/data/life/LifeNoteCodec.kt#L126) считает любой неограждённый H1/H2 границей поля. [persistDraft](../app/src/main/java/dev/stanislav/focusdeck/ui/life/LifeViewModel.kt#L198) сохраняет черновик через `create`, а восстановление — через `parse`.

Ввод в ожидание `За неделю три занятия\n## Условия\nБез командировок` после восстановления даёт полю только первую строку. Неизвестная секция ещё остаётся в исходной строке, но повторный `create` из восстановленных полей её уже не включает. При новом сохранении после перезапуска текст может потеряться. Заголовок, совпадающий с управляемым, дополнительно создаёт неоднозначность. Текущие тесты проверяют обычные переносы и ограждённые блоки, но не этот путь восстановления.

**Минимальное исправление:** сохранять точный локальный текст черновика независимо от ограничений формата секций либо запретить/безопасно преобразовать только конфликтующие заголовки с явным предупреждением. Не сообщать «Сохранено», если повторный parse меняет поля или выявляет ошибки. Не ограничивать обычную длину размышления ради исправления формата.

### R4 · P1 · Отсрочка выдаётся за состоявшийся обзор

**Факт кода:** [postponeReview](../app/src/main/java/dev/stanislav/focusdeck/ui/life/LifeViewModel.kt#L138) меняет и `reviewDate`, и `reviewedOn = today`, хотя результат не вводился. Напротив, запись результата в `prepare` обновляет `reviewedOn`, но автоматически не разрешает судьбу прежней `reviewDate`; [needsReview](../app/src/main/java/dev/stanislav/focusdeck/data/life/LifeEntry.kt#L83) её продолжает считать наступившей. Перевод `paused → active` также считается новым принятием решения.

**Минимальное исправление:** «Напомнить позже» изменяет только будущую дату; «Результат пока неизвестен» фиксирует именно неопределённость; «Проверить результат» сохраняет факт и предлагает продолжить с новой датой или закрыть. Возобновление и повторное принятие — разные события. Не скрывать запись из очереди через ложный `reviewedOn`.

### R5 · P2 · Черновик незаметно становится обязательством на неделю

**Факт кода:** [draft](../app/src/main/java/dev/stanislav/focusdeck/data/life/LifeEntry.kt#L109) назначает всем типам, кроме областей, дату через семь дней; `needsReview` включает `DRAFT` и `PAUSED`. `reviewsDue` возвращает их без различения. Недельный обзор, созданный специальным методом, очищает дату; обычный `draft(REVIEW)` — нет. Следовательно, модель очереди смешивает идеи, отложенные дела и действительные договорённости. Реальное отображение очереди в новом экране пока не проверено.

**Минимальное исправление:** черновику по умолчанию не назначать обязательный пересмотр. Дату напоминания можно выбрать отдельно; пауза должна явно означать «без напоминаний» или «вернуться тогда-то». Семь/тридцать дней — редактируемое предложение, не научная норма. При возвращении после перерыва дать выбрать одно актуальное дело, а не навязывать разбор всего накопившегося.

### R6 · P2 · Следующее действие и вывод обзора пока не замыкают цикл

**Факт кода:** `NEXT_ACTION` — текст, `CHANGE` — текст; [addActionToDay](../app/src/main/java/dev/stanislav/focusdeck/ui/life/LifeViewModel.kt#L181) создаёт дневную задачу, но не связывает её идентификатор с этим следующим шагом. После выполнения подсказка проекта остаётся прежней; повторное добавление допускается, потому что поиск дубля исключает выполненные задачи. `IF_THEN` хранится у цели/проекта; в просмотренном коде нет передачи этого плана в контекст старта задачи. Существующая подсказка возврата на Главной читает другое поле дневного ритуала.

**Минимальное решение P0:** не выдавать текст за невыполненную задачу; показать «Шаг уже добавлен/выполнен» там, где это надёжно известно, и предложить «Другой шаг» либо явное «Повторить». В обзоре дать переход к нужному проекту или созданию действия с заранее заполненным текстом и датой. Допустим вывод «Ничего не меняю» — создание новой задачи не должно быть условием окончания обзора. Для «если—то» разрешить условие начала, а не только помеху; не рекламировать автоматическую помощь в старте, пока план не виден в этом контексте.

### R7 · P2 · Статистика недели легко превращается в оценку человека

**Факт кода:** [loadWeekFacts](../app/src/main/java/dev/stanislav/focusdeck/ui/life/LifeViewModel.kt#L166) считает запланированные и выполненные запланированные задачи и дни с текстом дневника. Незапланированные выполненные дела не входят в эти счётчики. `readDailyNote` может возвращать `null` и при отсутствии файла, и при ошибке чтения; `mapNotNull` объединяет эти случаи. Полезное различие `availableDays / elapsedDays` уже есть, но само по себе не объясняет причину неполноты.

**Риск:** назвать эти числа «прогрессом целей», «дисциплиной» или «качеством недели»; считать копии дневных попыток уникальными результатами. Этого не обосновывают исследования самонаблюдения.

**Минимальное решение:** подпись «Выполнено X из Y задач, которым назначалось время, по N прочитанным заметкам». При нулевом знаменателе — «Нет задач с назначенным временем», не 0% успеха. Отсутствующие данные, ошибку чтения и будущие дни различать. В начале недели не выдавать текущие два дня за завершённую прошлую неделю: `beginWeeklyReview` выбирает текущий понедельник–воскресенье. Честное название периода важнее дополнительной аналитики.

## Продуктовые границы, которые сохранить

**Иерархия — гипотеза организации.** Необязательные `areaId/goalId/projectId` сохранить. Типовые области — редактируемые примеры, а не обязательный «баланс жизни». В UX есть конкретная ошибка контракта: строка 140 перечисляет для `kind` значения `area_id/goal_id/project_id`; код ожидает `area/goal/project`. Иначе заметка по этому примеру не распознается. Исправление документа — задача его владельца.

**Прекращение не равно достижению.** `DONE` для цели называется «Достигнута» и требует свидетельства; `PAUSED` и `ARCHIVED` доступны, отдельного отказа нет. Это допустимо в P0, если есть явная команда «Больше не планирую» → архив с причиной, без фиктивного достижения. Аналогично решение можно отменить до появления результата: «не проверял, отменил» — не наблюдённый отрицательный исход. Не заставлять пользователя придумывать успешный результат, чтобы закрыть обязательство.

**Квоты выбраны владельцем.** 100 слов, 600 букв/цифр, 20 разных слов и 540 минут/60% дня относятся к существующему ежедневному ритуалу. Они не следуют из evidence и не становятся критерием качества рефлексии. Сохранить ранее согласованное поведение; не переносить квоты в цели, решения и недельные обзоры. «60%» — покрытие окна 08:00–23:00 планом, не доля выполненных дел и не оценка продуктивности. Отдых, еда и дорога считаются согласно действующему правилу; повышать норму работы из этого нельзя.

## Приёмочные сценарии для владельца реализации

Использовать вымышленные заметки и отдельный QA-vault. Проверять итоговый Markdown после повторного чтения и перезапуска, а не только сообщение об успехе. Это список проверок, не отчёт об их прохождении.

| ID / риск | Дано → действие | Требуемый результат |
|---|---|---|
| A1 / R1 | Принято A с ожиданием «три занятия»; одним сохранением записать факт «два» и новый выбор B с ожиданием «одно» | История отдельно содержит первоначальное ожидание, новый факт и новую версию решения; ни одна запись не выдаёт старый факт за новый |
| A2 / R1 | Впервые ввести решение уже после известного исхода | Пометка «Записано после результата»; никакого заявления, что ожидание зафиксировано заранее |
| A3 / R1 | После принятия изменить только критерии/срок; затем отдельно исправить вывод | Датированные изменения различимы; предыдущие критерии, срок и вывод доступны; повтор без изменений не создаёт событие |
| A4 / R1–R2 | Принятая внешняя заметка без даты принятия/истории | Сообщить об отсутствии исходной записи; сохранить доступ к текущему тексту, не сочинять первоначальное ожидание |
| A5 / R2 | На Mac очистить ожидание; на телефоне изменить название активного решения | До записи проверить объединённый результат; не сохранить активное решение с незаметно нарушенным условием принятия |
| A6 / R2 | На Mac изменить прогноз; на телефоне записать факт по старому прогнозу | Перечитать/сопоставить версии или остановить операцию; черновик сохранён; нет молчаливой новой пары «прогноз — факт» |
| A7 / R3 | Вставить в поле H2, затем закрыть процесс и восстановить черновик; отдельно попробовать совпадающий управляемый заголовок | Точный текст доступен целиком либо показана понятная ошибка до принятия ввода; нет тихого обрезания при следующем сохранении |
| A8 / R4 | Нажать «Напомнить позже», затем в другой день действительно проверить | Первая операция не меняет дату последнего обзора; вторая сохраняет факт и явное решение о следующей проверке/закрытии |
| A9 / R5 | Создать 20 идей и поставить проект на паузу; вернуться через две недели | Нет 21 автоматически созданного обязательства; доступны выбранные напоминания и простой возврат без заполнения пропущенных дней |
| A10 / R6 | Добавить шаг проекта, выполнить его, снова открыть проект и нажать добавление | Выполненный шаг не выдан за ещё невыполненный; повторение является явным новым намерением |
| A11 / R6 | Закончить обзор выводом «Сохраню текущий режим»; второй обзор — конкретным экспериментом | Первый завершается без новой задачи; второй позволяет открыть связанную цель/проект и назначить действие, не создавая его автоматически |
| A12 / R7 | Из пяти прошедших дней два прочитаны, один недоступен; в одном файле есть выполненная задача без времени | Полнота и ошибка обозначены; задача без времени не объявлена провалом; будущие дни не входят в знаменатель; при Y=0 нет 0% |
| A13 / границы | Создать задачу без связей, проект без цели; закрыть утратившую смысл цель | Все пути доступны; отказ не называется «Достигнута» и не требует выдуманного доказательства успеха |
| A14 / квоты | Короткая цель, решение и недельный обзор; отдельный ежедневный ритуал с 539/540 минутами и пересечениями | Life-формы не наследуют дневниковые квоты; ритуал сохраняет согласованные правила и не обозначает покрытие как результативность |
| A15 / R4–R7 | Отложить на текущую/прошлую дату; открыть экран через полночь; начать обзор в понедельник | Нет бесконечного скрытого повторения проверки; дата операции и период видны; устаревшая очередь обновляется; текущая неделя не названа прошлой |

Первые обязательные проверки для сценария решений: **A1, A2, A5, A6, A7, A8**. ## Рекомендуемые тексты интерфейса

Это предложения владельцу UI, не уже внесённые изменения.

| Место | Текст |
|---|---|
| Первый вход | «Можно начать с задачи или проекта. Связи с целями и областями необязательны» |
| Личная причина | «Почему я выбираю это сейчас? Интерес, важность и обязательства могут сочетаться» |
| Условие действия | «Когда или после чего начну? Если возникнет помеха, что сделаю?» |
| До принятия решения | «Запиши, чего ожидаешь и к какому сроку. Краткого ответа достаточно» |
| Проверка решения | «Вот ожидание, сохранённое при принятии. Что стало известно теперь?» — только если такой снимок действительно есть |
| Нет исходного снимка | «Исходное ожидание не сохранено. Текущая запись не показывает, что было известно до результата» |
| Перенос проверки | «Напомнить позже»; результат: «Дата напоминания изменена. Проверка ещё не проведена» |
| Неопределённый результат | «Пока нельзя оценить» → «Когда вернуться к вопросу?» |
| Очередь обзоров | «Выбранные напоминания» / «Пора вернуться к этим записям», без «долга» и «провала» |
| Недельный вывод | «Что попробую изменить или сохраню как есть?» |
| Отказ от цели | «Больше не планирую»; «Запись останется в архиве. Это не отметка о достижении» |
| Правило ритуала | «Выбранное правило: запланировать 9 часов в окне 08:00–23:00. Отдых, еда и дорога тоже считаются» |
| Дневниковая квота | «Минимальный объём по выбранному правилу ритуала», без «достаточная рефлексия» или «научная норма» |
| Сохранение | «Записано в файл Obsidian на этом устройстве»; не «Синхронизировано» без проверки синхронизации |

Не использовать: «научно доказанная система жизни», «оптимально три проекта», «успешная неделя = 60%», «решение оказалось верным» только по удачному исходу, «дневник повысил продуктивность на X%». Для продукта достаточно: «В системе используются отдельные приёмы, изучавшиеся в исследованиях. Полный сценарий FocusDeck ещё не проверен».
