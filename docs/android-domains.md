# Android: ограниченная DNS-проба без сброса устройства

Выбран реализуемый кандидат: локальный `VpnService` с одним маршрутом к виртуальному DNS `10.111.0.2/32`, только для явно выбранных пакетов. Код находится в `domainfilter/`, использует офлайн IPv4/UDP-парсер и NXDOMAIN из `data/network/`. Это кандидат для контролируемой QA-проверки, не подтверждённая всеобщая блокировка сайтов. Запуск реального VPN здесь не выполнялся; интеграцию разрешений, экрана и проверку Pixel ведёт отдельный Android-исполнитель.

## Почему этот вариант

| Вариант без сброса | Что позволяет | Почему выбран / ограничение |
|---|---|---|
| Локальный DNS-only VpnService | Собственная политика доменов и короткий эксперимент для выбранных приложений | Выбран: поддерживаемые публичные API, без Device Owner, MITM и чтения URL. Занимает единственный VPN-слот; защита только для перехваченного обычного DNS |
| Private DNS / фильтрующий DNS-провайдер | Ручная настройка пользователем системного резолвера | Не меняется автоматически: глобальная настройка, внешний провайдер и его правила/хранение требуют отдельного выбора. Программная установка системного провайдера через DevicePolicyManager требует полномочий владельца устройства |
| Расширение браузера | Правила внутри поддерживаемого браузера | Не покрывает другие приложения. Chrome Web Store официально не устанавливает расширения на мобильном Chrome |
| Accessibility URL / экранный контроллер | Может наблюдать доступное дерево интерфейса | Не выбран для сайтов: более широкий доступ к содержимому окон, различия адресных строк и устаревшие узлы; не является сетевым фильтром |
| Полный VPN с анализом TLS / локальный MITM | Более широкий перехват трафика | Не выбран: другой масштаб обработки и риск для VPN/сертификатов; здесь нет MITM, установки CA, сброса или provisioning |

Основания: [официальное руководство VpnService](https://developer.android.com/develop/connectivity/vpn), [DevicePolicyManager и Private DNS](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#setGlobalPrivateDnsModeSpecifiedHost(android.content.ComponentName,java.lang.String)), [совместимость Chrome Web Store](https://support.google.com/chrome_webstore/answer/1698338?hl=en), [AccessibilityService и чтение содержимого окон](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService).

## Точная граница правил

`DomainPolicy.blockedDomains` — **точное имя**. `blocked.example` не блокирует `sub.blocked.example`, `notblocked.example` или `blocked.example.evil.test`. Поддеревья задаются отдельно в `blockedSubdomainTrees`. Регистр и завершающая точка нормализуются при запросе; политика заранее требует канонические ASCII-имена. URL, пути, порты и шаблоны не принимаются; IDN нужно явно преобразовать в punycode до конфигурации.

Защищённые инфраструктурные деревья `gitlab.eskhata.com`, `openai.com`, `chatgpt.com` не могут быть перекрыты блокирующим правилом. Пакеты OpenVPN, V2Box, Codex и системной оболочки не допускаются в список приложений пробы. Дополнительно исключаются доступные пакеты, объявляющие сервис с `BIND_VPN_SERVICE`; недоступные сведения о сервисах считаются причиной не перехватывать приложение. Разрешён только непустой явный список максимум восьми пакетов; первоначальная QA-проба должна использовать исключительно пакет `.qa` / собственный тестовый клиент, не браузеры и рабочие приложения пользователя.

Нет маршрута `0.0.0.0/0` или `::/0`: обычный HTTP, корпоративная сеть и прочий трафик не проксируются через приложение. IPv6 разрешён в обход, не объявлен заблокированным. Домен, уже полученный из кэша, прямой IP, встроенный/альтернативный резолвер, DoH/DoT/DoQ и произвольный DNS за пределами виртуального адреса могут обходить эту пробу. ECH/QUIC не разбираются и не превращаются в угаданное имя. TCP DNS и DNS payload свыше 1232 байт пока не поддерживаются: для такого запроса покрытие отсутствует и возможен сбой разрешения выбранного приложения. Остальные пакеты не включаются в эту пробу.

## Сохранение существующего VPN и Private DNS

Android предоставляет одному приложению право VPN; согласие другому отзывает прежнее. Поэтому **до вызова `VpnService.prepare()`** интерфейс обязан показать конфликт и не продолжать при обнаруженном VPN. Сервис повторяет проверку непосредственно перед `establish()`, но публичного атомарного «установить, только если другой VPN отсутствует» API нет. Пользователь должен видеть этот риск до системного согласия. `prepare()` не вызывается скрыто сервисом. Автоматических переподключений после отзыва, перезапуска процесса или загрузки устройства нет; `START_NOT_STICKY`, always-on должен быть отключён метаданными Manifest. [Официальная семантика согласия, отзыва и always-on](https://developer.android.com/reference/android/net/VpnService).

Для разрешённых имён используется `DnsResolver.rawQuery` с явно выбранной валидированной **не-VPN** сетью, без собственного UDP-клиента к публичному DNS, без изменения настроек DNS. API позволяет выбрать сеть и вернуть сырой DNS-ответ. [DnsResolver](https://developer.android.com/reference/android/net/DnsResolver).

Сохранение шифрования Private DNS этим путём пока не подтверждено реальным тестом, поэтому проба **отказывается стартовать** при `isPrivateDnsActive=true` или непустом `privateDnsServerName`. Если эти признаки появляются во время работы, проба закрывается; настройка пользователя не меняется. Не нужно выключать Private DNS ради прохождения QA. Официальная документация требует не отправлять открытые DNS-запросы при активном Private DNS; строгий режим требует указанного имени и проверки сертификата. [LinkProperties](https://developer.android.com/reference/android/net/LinkProperties), [рекомендации Android по безопасному DNS](https://developer.android.com/privacy-and-security/risks/bad-dns).

Между проверкой и изменением сети остаётся гонка наблюдений. Поэтому код не заявляет доказанную совместимость с динамическим Private DNS: это отдельный эксплуатационный блокер до контролируемой проверки.

## Запуск, пауза и восстановление

Сервис `DomainFilterVpnService` принимает только явный `ACTION_START` с JSON в `EXTRA_POLICY`:

```json
{
  "sessionId": "3de91f5b-6690-46f4-96c7-19a8849fc11e",
  "blockedDomains": ["blocked.example"],
  "blockedSubdomainTrees": [],
  "protectedDomains": ["gitlab.eskhata.com", "openai.com", "chatgpt.com"],
  "allowedPackages": ["com.android.chrome"],
  "durationSeconds": 1500,
  "consentVpnReplacementRisk": true
}
```

Политика фиксируется на время пробы; повторный START не подменяет действующую. Для обычного пользовательского окна, включая поставляемый QA APK, базовый срок — 25 минут. Одна ограниченная пауза продлевает его максимум на 300 секунд, общий предел — 30 минут (1800 секунд). Источник истины — независимое сохранённое `ProtectionWindow`, его монотонный срок и единственная пауза. Это длительность ограничений, не доказательство 25 минут работы. Доменный JSON должен точно совпадать с замороженным снимком окна и sessionId; fingerprint дополнительно фиксируется по ID окна.

`ACTION_PAUSE` обычного окна использует общий `beginRelief()`. По окончании паузы правила возвращаются, работа пользователя — нет. Прямой `ACTION_STOP` внутри действующего окна отклоняется. Действие уведомления «К полному выходу» только открывает существующую карточку; оно не начинает отсчёт и не меняет ограничения. Пользователь отдельно выбирает полный выход с коротким 15-секундным подтверждением без эссе. После подтверждения или окончания окна TUN закрывается.

Быстрый технический откат выделен **только** для синтетической пробы: явный `EXTRA_QA_TRIAL=syntheticQaTrial`, debuggable `.qa`, единственное имя `blocked.test`, только собственный QA-пакет, без поддеревьев и с базовыми инфраструктурными исключениями. Суммарный срок этой пробы — не более 120 секунд, включая паузу. Для неё STOP мгновенный. Сам debuggable-флаг обычному QA-окну обхода не даёт; JSON выше описывает обычный пользовательский снимок и требует действующего независимого окна.

Отзыв системного VPN-согласия, исчезновение безопасной исходной сети и истечение срока закрывают TUN в любом режиме. Системное отключение VPN всегда остаётся обходом владельца, оно не блокируется. Нет постоянной переустановки или скрытого восстановления. При ошибке сеть освобождается, статус остаётся неполной/неактивной защитой. Это описание поведения исходников, а не заявление о пройденной живой QA.

До установления TUN сервис требует включённых уведомлений, чтобы сохранялся видимый путь остановки/полного выхода. Разрешённые DNS-запросы ограничены 32 одновременными, таймаутом 5 секунд и проверкой соответствия вопроса/ID ответа. DNS-имена и URL в журналы не пишутся. В памяти UI доступны только состояние и счётчики blocked/forwarded/unknown; они не являются метрикой фокуса или полезности.

## Проверка перед утверждением «работает на Pixel»

1. Собрать unit tests, QA APK и интегрировать non-exported VpnService/foreground permissions/явный экран согласия. Офлайн тесты проверяют точные имена, инфраструктуру, монотонный срок/одну паузу, IPv4/UDP checksums, ID/вопрос ответов и Unknown для неподдерживаемых пакетов.
2. Terra проверяет foreground устройства перед управлением и использует вымышленный QA-профиль. Нет существующего VPN; Private DNS не изменяется. При конфликте проба должна отказаться, а не обходить его.
3. Только после явного системного согласия: собственный QA-клиент получает NXDOMAIN для выбранного тестового имени; разрешённый вопрос получает ответ платформенного DNS; рабочий трафик вне выбранного пакета сохраняется. Отдельно проверить остановку, срок и возврат после паузы.
4. Проверить Private DNS/смену сети, отзыв согласия и отсутствие рестарта после остановки. После теста закрыть пробу и подтвердить отсутствие VPN-интерфейса/изменённых системных DNS-настроек.

Unit/пакетные тесты не доказывают реальную DNS-маршрутизацию, Private DNS, кэши, браузеры или пригодность длительного режима. Пока эти проверки не пройдены, продукт должен показывать «частичная экспериментальная DNS-проба», а не «сайты защищены».

## Пользовательская настройка и интеграция production

`DomainSettingsPanel` — необязательная одноразовая настройка: список явных приложений, точные отвлекающие имена, рабочие исключения и отдельное подтверждение VPN-риска. По умолчанию будущие окна выключены. Сохранённый выбор не является подтверждением активного VPN. Изменение выбора отключает применение к новым окнам до повторного явного согласия; действующий снимок остаётся прежним.

Приложение создаёт один `DomainFilterController(applicationContext, auditSink)` после `protectionStore`. Его конструктор только читает настройки и наблюдает за статусом — не вызывает prepare, не запускает VPN и не получает согласие автоматически. Compose-панель использует обычный Activity Result системного диалога. После перезапуска процесса отображается фактическое отсутствие службы; для восстановления нужно явное действие запуска текущего снимка и действующее системное согласие.

Интерфейс интеграции:

- `snapshotForSession(sessionId)` возвращает JSON только при сохранённом явном включении; вызывается при старте выбранной задачи.
- `ProtectionWindowStore.begin(..., domainPolicyJson=...)` сохраняет его отдельно от `packages` app-gate. Пустой app-gate список допустим только при валидном DNS-снимке; браузер не становится приложением, которое надо закрывать целиком.
- `onWindowReady()` вызывается после успешного старта задачи/окна. Использует только замороженную политику текущего окна. Неизвестное согласие, другой VPN или Private DNS означают отказ и честный статус, а не молчаливую защиту.
- `DomainSettingsPanel(controller, installedApps, onRequestFullExit)` получает от приложения доступные браузеры/явно выбранные пакеты. Полный выход ведёт в тот же существующий flow окна защиты; уведомление передаёт `EXTRA_REQUEST_EXIT=focusdeck.requestDomainExit` в MainActivity.
- `disableFutureWindows()` отключает только новые окна. Обычного мгновенного выключателя действующей production-защиты нет; системное отключение VPN остаётся доступным обходом владельца.

`DomainAuditSink` получает только v1 `health`/`disabled`: активность частичного DNS, отказ, недоступность, выключение будущих окон. Фокус/отвлечения/обслуживание остаются `null`; имена запросов не записываются. Первичное неактивное состояние никогда не настроенной службы не создаёт ложное событие отключения. Глобальные ошибки настройки имеют `sessionId/category=null`; известный переход действующей DNS-сессии связывается только с её собственным sessionId. Sink внедряется в существующую атомарную очередь аудита приложения, не подменяет Room-журнал сессий вторым экспортером.

Четыре модельных теста дополнительно проверяют OFF по умолчанию/отказ согласия, отличие сохранённой настройки от runtime, заморозку будущего/действующего выбора и отказ неполной области до согласия. Реальную загрузку SharedPreferences, consent-экран и production-вызов `onWindowReady` необходимо подтвердить в интегрированном APK; чистые JVM-тесты не заменяют эту проверку.


Важное различие поставляемого QA APK: обычная пользовательская политика использует production-путь с независимым окном и полным выходом. Исключение для быстрого отката ограничено описанным синтетическим scope и проверяется сервисом; обычный Intent с debuggable-флагом его не включает. Динамические исключения Phone/SOS/Settings/launcher/keyboard проверяются при выборе, формировании снимка, preflight, непосредственно перед establish и во время пробы; собственный пакет допускается только узкой синтетической QA-пробой. Кнопка уведомления лишь навигирует к существующей карточке: exported Activity не получает право снять ограничение или начать отсчёт по одному boolean-extra.

## Подтверждённая ограниченная проверка — 28 октября 2026

Android-исполнитель сообщил результат контролируемой живой проверки собственного `.qa` клиента: uncached `blocked.test` вернул NXDOMAIN (`rcode=3`), счётчик блокировки увеличился до 1; uncached `example.com` вернул `rcode=0`, счётчик передачи — 1. `unknown=9`; причины по отдельным запросам не записывались. После явной остановки синтетической пробы `active=false`, VPN-сеть отсутствовала, Private DNS остался выключенным, как до пробы.

Это подтверждает ограниченный DNS/TUN round-trip и восстановление именно тестового клиента на данном Pixel. Это не проверка всех браузеров, приватных окон, DoH/DoT, режима активного Private DNS, конфликта с рабочим VPN или непрерывного production-окна на 30 минут. Интерфейс должен сохранять эти границы, даже когда тестовые NXDOMAIN и разрешённый ответ прошли.
