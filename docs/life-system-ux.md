# FocusDeck: жизненная система и мобильный UX

Дата: 29 сентября 2026. Статус: предложение для четырёхчасовой реализации, уточнено по текущим LifeEntry/LifeNoteCodec основного агента. Это спецификация, а не описание уже реализованного функционала. Изменяется только этот документ.

## 1. Решение для реализации сейчас

Сохранить четыре вкладки: **Главная / План / Дневник / Приложения**. На Главной добавить одну карточку **«Сферы и цели»**, открывающую внутренний раздел. Папки в Obsidian: `FocusDeck/{Области,Цели,Проекты,Решения,Обзоры}`. Одна сущность — один обычный `.md`, постоянный UUID, плоский YAML frontmatter, размышления в читаемых `##` секциях. Между сущностями — ID как основание связи, wikilinks в тексте для навигации в Obsidian.

**Задачи остаются в существующих дневных заметках.** Ни отдельного файла задачи, ни второго чекбокса в проекте в P0. Проект задаёт контекст задачи через `[project:: UUID]`; сам чекбокс — единственное место её выполнения. Все изменения дневных заметок идут через существующий `VaultDayStore`. Новое хранилище жизненной системы никогда не перезаписывает daily note самостоятельно.

Первую задачу можно записать без создания области, цели, проекта, решения или обзора. Иерархия помогает разобраться, зачем делать задачу, но не является обязательной цепочкой форм.

**P0 вертикальный сценарий:** создать проект → добавить действие в день → разместить его в существующем Плане → выполнить на Главной → увидеть связь с проектом. Дополнительно минимально работают принятие/пересмотр решения и сохранение короткого недельного обзора. Общий бессрочный backlog, полный граф связей и количественные панели прогресса — P1.

## 2. Что проверено в существующей системе

| Основание | Следствие для реализации |
|---|---|
| `ui/root/RootScreen.kt`: четыре вкладки, внутренние overlays, отдельная ветка обязательного ритуала | Добавлять внутренний маршрут/overlay, не пятую вкладку. Новые разделы не должны обходить обязательный ритуал. |
| `ui/home/HomeScreen.kt`: фокус/следующее дело, задачи, лента дня, метрики, вечерняя подготовка | Карточка жизненной системы ниже текущего действия и задач, до второстепенных метрик. Не вытеснять запуск фокуса. |
| `PlanningViewModel`: задачи берутся из `dayStore.note`; пул привязан к выбранной дате | В P0 «без времени» означает «в плане этого дня без слота», а не общий inbox. |
| `HomeViewModel` читает `todayNote`, независимо от выбранного в Плане дня | Добавление на завтра не должно подменять сегодняшние задачи на Главной. |
| `DailyNoteParser`: секция `## Задачи`, checkbox, `⏳ HH:mm` / `[time:: HH:mm]`, `[dur:: N]` | Сохранить действующий формат; расширить только метаданные связи и идентичности. |
| `VaultTask.id` сейчас равен номеру строки; `resolveTask` может искать первый совпавший title | Это временный ключ UI, не постоянный ID. Нужна однозначность после внешних правок и для одинаковых названий. |
| `renameTask` пересобирает хвост только из времени и длительности | Наивное добавление project/ID потеряет связь при переименовании. Это обязательная точка изменения парсера. |
| `copyUnfinishedTaskToDay` сравнивает title и создаёт новую строку | Сохранить существующую семантику копии обещания на новый день; не выдавать её за перенос единой глобальной задачи. |
| `VaultDayStore`: общий mutex, перечитывание перед записью, оптимистический UI | Использовать тот же канал записи; при ошибке откатывать отображение и оставлять понятное повторное действие. |
| `VaultRepository`: SAF, полная запись содержимого, поиск daily в корне и на один уровень ниже | Новые сущности искать только в известных пяти папках. Не расширять поиск daily на весь vault. |
| `docs/discipline-ritual.md`: действующие обязательные ритуалы и пороги владельца | Этот UX-документ не меняет 540 минут плана, критерии дневника, питание и ограничения лаунчера. |

Read-only проверка настроенного vault: прочитан один обычный daily note и две заметки о жизненном планировании. Подтверждены текущая структура daily, существующие свободные записи о направлениях жизни и пустая проектная заготовка. В выдаче уже присутствуют `.sync-conflict` файлы. Личные тексты здесь не копируются; существующие заметки не мигрируются автоматически.

Оригинальный HTML-макет не найден среди HTML-файлов репозитория вне `architecture-workboard` и при ограниченном поиске на Desktop/Downloads. Архитектурный workboard не принят за макет FocusDeck. Визуальная основа отчёта — существующие Compose-компоненты, а не предполагаемый дизайн. Телефон и запущенное приложение не исследовались.

## 3. Продуктовые ориентиры, не доказательство эффективности

- **Obsidian:** properties поддерживают обычный YAML, типизированные значения и списки; сложную вложенную модель в properties не закладываем. Встроенные ссылки в YAML требуют кавычек; в нашем контракте навигационные ссылки находятся в теле. [Официальные Properties](https://help.obsidian.md/properties).
- **Obsidian:** wikilinks позволяют ссылаться на заметку и конкретный блок; block ID допускает латинские буквы, цифры и дефисы. Применяем UUID и `^task-UUID`. Такие ссылки являются расширением Obsidian, а не универсальной возможностью Markdown. [Официальные Internal links](https://help.obsidian.md/links).
- **GTD:** разделяем запись мысли, уточнение действия, организацию, обзор и выполнение. Это вдохновляет быстрый ввод без обязательной полной классификации. [Официальное описание GTD](https://gettingthingsdone.com/what-is-gtd/).
- **GTD review:** обзор должен возвращать актуальность обязательств и следующих действий; допускается начать с части обзора. Наши три вопроса ниже — собственное упрощение, не полный официальный GTD checklist. [GTD Best Practices: Review](https://gettingthingsdone.com/2011/11/gtd-best-practices-review-part-4-of-5/).
- **PARA:** различаем постоянную область ответственности и проект с конечным результатом; справочные материалы остаются ссылками в Obsidian, завершённое уходит из активного представления. Не переустраиваем весь vault в PARA и не создаём отдельные вкладки Resources/Archives. [Материал автора PARA](https://fortelabs.com/blog/para/).
- **Syncthing:** параллельное изменение файла на устройствах может породить отдельную конфликтную копию, которая также синхронизируется. Поэтому «записано локально» не равно «синхронизировано». [Официальное описание конфликтов](https://docs.syncthing.net/users/syncing.html#conflicting-changes).

Ни количество приоритетов, ни длительность обзора, ни предлагаемые поля не объявляются научно установленными нормами. Научные основания и ограничения выводов — отдельная работа агента evidence.

## 4. Смысл сущностей и связи

| Сущность | Вопрос пользователя | Пример, не пользовательские данные | Связь |
|---|---|---|---|
| Сфера (`area`, папка `Области`) | Что хочу поддерживать постоянно? | Здоровье | Родителя нет |
| Цель (`goal`) | Какого изменения хочу достичь? | Пробежать 5 км без остановки | Необязательный `area_id` |
| Проект (`project`) | Какой конечный результат сейчас создаю? | Пройти вводную программу бега | Необязательные `area_id`, `goal_id` |
| Действие (daily checkbox) | Что конкретно сделаю следующим? | Выбрать три занятия на неделю | Необязательный `project` из `[project:: …]` |
| План дня | Когда беру действие в работу? | Сегодня, 18:30, 30 минут | Дата daily и поля времени задачи |
| Решение (`decision`) | Что выбираю, почему и когда проверю? | Заниматься утром две недели | Необязательные `area_id`, `project_id`; review date |
| Обзор (`review`) | Что произошло и что изменю? | Обзор 28 сентября — 4 октября | Период + ссылки на обсуждаемые сущности в тексте |

У цели и проекта один основной родитель каждого допустимого типа; дополнительных родителей P0 не предлагает. Проект без цели — нормальная ситуация. Если у проекта задан `goal_id`, его область берётся из цели; при записи `area_id` это значение должно совпадать. При противоречии во внешнем Markdown ничего не исправлять молча: показать «Проверьте связь со сферой» и предложить выбор в редакторе. Проект без связей отображается как «Без сферы»; фиктивный файл такой области не создавать.

Не вычислять достижение цели как процент выполненных задач. Чекбоксы отражают действия, достижение цели — проверку результата человеком. Завершение проекта не завершает цель автоматически. Архивация области не архивирует её потомков и не отменяет задачи.

## 5. Навигация и мобильная иерархия

Главная сохраняет первенство текущего действия. Карточка **«Сферы и цели»** содержит одну вторую строку: сначала «Есть решения для пересмотра», иначе «Подведите итоги недели», иначе число активных проектов. Никаких красных суммарных оценок жизни. Отсутствие подключённого vault показывает действие подключения вместо нулевых счётчиков.

Внутренний экран «Сферы и цели»:

1. Короткий раздел **«Сейчас»**: до трёх активных целей/проектов; при отсутствии — «Создать проект». Это ограничение превью, а не ограничение количества сущностей.
2. **«Сферы»**: список с кратким количеством активных целей/проектов. Нажатие открывает сферу → цель → проект; дочерние списки плоские.
3. Две строки входа: **«Решения»** и **«Обзор недели»**. Не превращать их в новые нижние вкладки.
4. «Все проекты» и архив — менее заметные текстовые действия. Архивный список можно отложить в P1, но статус должен читаться уже в P0.

Карточка проекта: название → «Готово, когда» → контекст сферы/цели → задачи выбранного дня → основная кнопка **«Добавить действие в план»**. В P0 явно писать «Действия на 29 сентября», если показана лишь дневная выборка. Нельзя обещать «Все действия проекта», когда индексируются только открытые дни.

Редактор: название видно сразу; родитель и статус — компактные поля; дополнительные размышления раскрываются ниже. Основная кнопка «Сохранить», при новом действии — «Добавить в план». Одна основная кнопка на экран. Для статусов показывать русский текст, enum оставлять только в файле.

Использовать текущие `FocusCard`, `FocusButton`, typography и отступы 8dp. Основные размеры текста 24/16/14sp; интерактивная область не меньше 48dp. Статус обозначать текстом, а не одним цветом. Учитывать клавиатуру, прокрутку формы и крупный системный шрифт. Back из проекта возвращает в прежний список с его позицией; Back из редактирования сохраняет локальный черновик. Сохранённая запись не должна зависеть от существования черновика.

## 6. Минимальные рабочие сценарии

### 6.1. Первая задача — без настройки системы

План → «Добавить задачу» → название → «Добавить». Дата — открытый день Плана; из Главной — сегодня. Проект необязателен и скрыт за полем «Проект». Время не назначается автоматически. Время/длительность выбираются существующим интерфейсом Планирования.

Готовность: задача переживает перезапуск, видна в Obsidian, выполняется из привычного интерфейса. На пути нет обязательных экранов создания области, цели или проекта.

### 6.2. От сферы к следующему действию

«Сферы и цели» → создать сферу только по названию → необязательно добавить цель с результатом → создать проект → «Добавить действие в план». Родительские ID подставляются из контекста. При создании проекта напрямую обязательным остаётся только название; «Готово, когда» можно дописать позже.

Форма действия: название, дата, необязательная длительность; проект уже выбран. После успеха коротко «Добавлено в план на 29 сентября» с действием «Открыть план». Переход открывает нужную дату и новую задачу. Если времени нет, задача остаётся в дневном пуле «Без времени».

Следующее действие формулируется глаголом и наблюдаемым результатом. Это подсказка и пример в поле, не автоматический фильтр русского языка.

### 6.3. Цель: обдумать, принять, пересмотреть

Новая цель начинается как `draft` («Обдумываю»). Для «В работу» нужны непустое название и секции «Почему это важно» (`WHY`), «Как пойму, что готово» (`SUCCESS`); срок необязателен. Можно добавить «Зачем» и «Что ограничивает». Не требовать числа или метрики для любой жизненной цели.

При недельном обзоре цель открывается с действиями «Продолжить», «На паузу», «Достигнута». Для «Достигнута» предложить коротко записать подтверждение результата; не вычислять его из задач. Пересмотр не переписывает исходное «Зачем» автоматически.

### 6.4. Решение: записать → принять → проверить

Быстрое создание: название вопроса, статус `draft` («Обдумываю»). Родитель необязателен. Можно сразу вернуться к задачам.

«Принять решение»: заполнить **«Варианты»** (`OPTIONS`), **«Мой выбор и основания»** (`CHOICE`) и **«Ожидаемый результат»** (`PREDICTION`); дату принятия сохранить в теле и предложить `review` через 7 дней. Короткие ответы допустимы, квоты слов нет. Варианты нужны для принятия, но не для сохранения черновика; цена выбора и прочие размышления раскрываются дополнительно. Действие после решения создаётся отдельно кнопкой «Добавить действие в план»: принятие решения не означает выполнения задачи.

Когда `review <= сегодня`, карточка попадает в «Пора пересмотреть». Открываются исходный выбор и критерий, затем поле **«Что получилось»** и три действия:

- «Продолжить» — сохранить итог, оставить `active`, выбрать следующую дату проверки.
- «Изменить» — сохранить исходный выбор в истории и принять обновлённый; снова указать проверяемое ожидание.
- «Отказаться» — записать итог и установить `done`.

Итог сохраняется в `OUTCOME/LESSON`; датированная история — в `HISTORY` («История решений»), с `decided_on/reviewed_on` в frontmatter. P0 допускает историю как Markdown-текст в той же заметке, без отдельной сущности события. Не удалять первоначальное обоснование. Просроченная дата — повод вернуться к решению, не «провал».

### 6.5. Недельная саморефлексия

Период — понедельник–воскресенье по локальной дате. Кнопка доступна всегда; ненавязчивое предложение на Главной — с воскресенья либо когда со времени последнего завершённого обзора прошло 7 дней. Никаких push-уведомлений и новых блокировок в P0.

Экран показывает период и три поля: **«Что получилось»**, **«Что мешало»**, **«Что изменю»**. Ниже — ссылки «Посмотреть цели и проекты» и «Решения для пересмотра», затем необязательное «Добавить действие в план».

P0 обзор может работать без автоматически собранной статистики: пользователь читает связанные записи и отвечает сам. Если данные недели собраны частично, писать «Доступно 3 из 7 дневных заметок», а не выводить нулевую продуктивность за остальные дни.

«Сохранить черновик» доступно всегда. Для «Завершить обзор» достаточно осмысленного непустого ответа «Что изменю»; допускается «Сохраню текущий режим». Остальные вопросы можно оставить пустыми. Ни обязательных чисел, ни требования создать новую цель. Завершение обзора не выполняет задачи и не завершает существующий ежедневный ритуал.

### 6.6. Возвращение после перерыва

Показать последний обзор и текущие активные проекты. Предложить выбрать одно следующее действие на сегодня; не требовать заполнить пропущенные дни или отчёты. Старые проекты можно поставить на паузу. Не переносить все незаконченные задачи автоматически.

## 7. Контракт файлов и полей P0

### 7.1. Общая оболочка

Папки: `FocusDeck/Области`, `FocusDeck/Цели`, `FocusDeck/Проекты`, `FocusDeck/Решения`, `FocusDeck/Обзоры`. Создавать нужную папку при первой записи, а не заполнять vault демонстрационными сущностями при запуске.

Файл по умолчанию: `<читаемое название> -- <UUID>.md` (текущий `LifeEntry.fileName`). UUID не меняется после переименования; P0 меняет `title` и H1, не имя файла. `id`, а не путь, имя или timestamp — идентичность. Все примеры ниже вымышленные.

| Поле | Требование |
|---|---|
| `id` | Обязательно. UUID строкой; создаётся один раз до отправки команды сохранения, повторный запрос использует тот же ID. |
| `kind` | Обязательно: `area_id`, `goal_id`, `project_id`, `decision`, `review`. |
| `title` | Обязательно для новой записи, однострочный текст. При ошибке внешнего файла можно показать basename как аварийную подпись, не записывать его назад. |
| `status` | Общий enum `draft / active / paused / done / archived`; подписи и предлагаемые переходы зависят от типа. |
| `created` | Автоматическая локальная дата `YYYY-MM-DD`, сохранять при редактировании. Не использовать для разрешения конфликтов. |
| `updated` | Дата последней записи приложения; не является revision или доказательством более правильной версии. |
| `focusdeck` | Маркер текущего codec: `1`. |
| `area_id`, `goal_id`, `project_id` | Необязательные UUID в допустимых типах. Отсутствующее или пустое значение означает отсутствие связи. |
| `due`, `review` | Необязательные календарные даты; соответствуют `dueDate` / `reviewDate` модели. |

Это имена полей текущего `LifeNoteCodec`: они заменяют предварительные `type / area / goal / project / review_on`. Kotlin enum — в верхнем регистре, wire-значения `kind/status` — в нижнем. Не вводить второй конкурирующий словарь.

Неизвестные frontmatter-поля и пользовательские секции сохранять. Не добавлять вложенный JSON, сериализованную модель в комментарии или обязательный Dataview/Tasks-плагин. YAML должен оставаться обычным YAML: строки с двоеточием и прочими спецсимволами корректно экранируются. Если выбранный парсер не поддерживает внешнюю конструкцию, показывать заметку для чтения с объяснением, не нормализовать её с потерей данных.

### 7.2. Поля и русские состояния

| Тип | Статусы, default выделен | Дополнительные поля P0 | Читаемые секции |
|---|---|---|---|
| `area` | **`draft`** «Обдумываю», `active` «Поддерживаю», `archived` «В архиве» | Нет обязательных | `STANDARD`: «Что значит достаточно»; дополнительно `WHY`, `EVIDENCE` |
| `goal` | **`draft`** «Обдумываю», `active` «В работе», `paused` «На паузе», `done` «Достигнута», `archived` «В архиве» | `area_id?`, `due?` (желаемая дата) | `SUCCESS`: «Как пойму, что готово», `WHY`: «Почему это важно»; остальное скрыто в дополнительных полях |
| `project` | **`draft`** «Обдумываю», `active` «В работе», `paused` «На паузе», `done` «Завершён», `archived` «В архиве» | `area_id?`, `goal_id?`, `due?` | `SUCCESS`, `NEXT_ACTION`: «Следующее действие»; дополнительно `OBSTACLE`, `IF_THEN`, `EVIDENCE` |
| `decision` | **`draft`** «Обдумываю», `active` «Принято», `paused` «На паузе», `done` «Закрыто», `archived` «В архиве» | `area_id?`, `project_id?`, `review?` | `CHOICE`: «Мой выбор и основания», `PREDICTION`: «Ожидаемый результат»; при пересмотре `OUTCOME`: «Что произошло», `LESSON`: «Что я понял»; `OPTIONS` нужен для принятия, `CRITERIA/COST` необязательны |
| `review` | **`draft`** «Черновик», `done` «Завершён» | `period_start`, `period_end` | `WINS`: «Что получилось», `FRICTION`: «Что мешало», `CHANGE`: «Что изменю»; `COMMITMENT`: «Главное на неделю» необязательно |

Заголовки берутся из `LifeField.heading`, не из английского имени enum. Общие enum допускают другие прочитанные состояния; таблица ограничивает лишь предлагаемые в конкретной форме переходы. Актуальный общий default — `DRAFT` для всех типов: короткая форма сохраняет черновик. Перевод в работу проходит `activationProblems()`: цель требует WHY/SUCCESS; проект SUCCESS/NEXT_ACTION; решение OPTIONS/CHOICE/PREDICTION и review date. Это не блокирует создание первой daily-задачи. Область можно активировать после названия. Короткое создание и принятие обязательства остаются разными действиями.

`review` обязателен именно при переходе решения в `active`; у черновика может отсутствовать. «Пора пересмотреть» вычисляется из даты, отдельного статуса `overdue` нет. У внешнего принятого решения без даты показывать «Назначьте пересмотр», не создавать дату автоматически. Неизвестные enum из Obsidian показывать как «Неизвестный статус» с исходным значением, без автоконвертации.

Для обзора одна основная запись на период: `period_start/period_end` задаются явно. Повторное открытие ищет по `kind=review + period_start + period_end`; UUID обычный, не производный от номера недели. При двух записях предложить выбор. Решение дополнительно использует `decided_on/reviewed_on`, а полную историю сохраняет в `HISTORY`. Даты созданы и читаются текущим codec; отдельные альтернативные поля не требуются.

### 7.3. Пример проекта

```markdown
---
focusdeck: "1"
id: "82e54193-d2aa-4f29-94b6-e8ac964c250e"
kind: project
title: "Подготовить портфолио"
status: active
created: 2026-09-29
updated: 2026-09-29
area_id: "9137420c-1dd5-46a8-8bb2-cb903982851d"
goal_id: "bbd0163a-7480-432d-a5a8-737b8c77c155"
---

# Подготовить портфолио

## Как пойму, что готово
Три кейса опубликованы и проверены по ссылке.

## Заметки
Начать с одного законченного примера.

## Связи FocusDeck
- [[FocusDeck/Области/Работа -- 9137420c-1dd5-46a8-8bb2-cb903982851d|Работа]]
- [[FocusDeck/Цели/Новая роль -- bbd0163a-7480-432d-a5a8-737b8c77c155|Новая роль]]
```

ID — источник связи в приложении. Wikilink — читаемая навигация по фактическому пути. При внешнем переименовании индекс ID → path обновляется после чтения. Не требовать совпадения имени файла с title. При расхождении ID и ссылки приоритет у ID; показать необходимость проверить ссылку, не заменять все ссылки vault автоматически.

**Pragmatic graph contract.** Сохранять исходящие wikilinks к родителям в `## Связи FocusDeck` при создании сущности и явном изменении родителя. Обратные ссылки в родительский файл не писать: Obsidian уже строит backlinks/граф, а одно сохранение должно менять один файл. Не выводить только UUID-поля в frontmatter: ребро графа требует внутренней ссылки. [Документация Graph view](https://help.obsidian.md/plugins/graph).

Индекс строится по `id` внутри файла, не по basename, поэтому внешний rename в пределах известных kind-папок переносится нормально. Если пользователь переместил файл за пределы этих папок, P0 показывает отсутствующую связь; полный поиск по vault — P1. Если файл реально переименован в Obsidian, опция **Files and links → Automatically update internal links** позволяет Obsidian обновлять ссылки. При отключённой опции он предлагает обновление; отказ оставляет потенциально сломанные ссылки. FocusDeck не меняет эту настройку пользователя. Rename другим приложением сам по себе такой гарантии не даёт. [Официальная настройка](https://help.obsidian.md/settings#Files%20and%20links).

`[[путь|Название]]` задаёт подпись конкретной ссылки; опциональный стандартный `aliases` помогает искать и вставлять ссылки в Obsidian. Alias и H1 не являются постоянным ID. Выбраны читаемые имена `<название> -- <UUID>.md`, чтобы узлы графа и файловый список были понятнее. При изменении title приложение не обязано переименовывать файл; имя может отражать исходное название. Все новые wikilinks строить из `LifeEntry.wikiLink/relativePath`, а не собирать имя повторно из title. [Официальные Aliases](https://help.obsidian.md/aliases).

Не пересобирать `## Связи FocusDeck` на каждом autosave из шаблонного `UUID.md`: это может откатить корректную ссылку после внешнего rename. Сохранять свежий текст секции, а при добавлении/изменении родителя использовать актуальный путь из ID-index и сохранять дополнительные пользовательские ссылки. Обновление всех старых подписей ссылок после изменения title не входит в P0.

`[project:: UUID]` на daily-задаче сам по себе не даёт ребра daily → project в стандартном графе. Если это ребро требуется уже сейчас, в той же операции `VaultDayStore` добавить обычный wikilink в отдельную секцию связей daily, вне `## Задачи`; не создавать второй writer. Минимальная P0-версия гарантирует граф между сущностями, а связь задач с проектом — внутри FocusDeck.

### 7.4. Формат задачи и обратной ссылки

В существующем `00 - 2026-09-29.md`:

```markdown
## Задачи

- [ ] Написать черновик первого кейса ⏳ 10:00 [dur:: 50] [project:: 82e54193-d2aa-4f29-94b6-e8ac964c250e] ^task-e6d64a67-28d4-4166-b579-0df038b03455
```

Ссылка из обычного текста Obsidian:

```markdown
[[00 - 2026-09-29#^task-e6d64a67-28d4-4166-b579-0df038b03455|Черновик первого кейса]]
```

Для daily в подпапке использовать фактический vault-relative path без `.md`. Генерировать task UUID до вызова transform: текущий optimistic transform может исполняться дважды. ID на конце строки — корректная адресация блока; изменение времени/длительности не должно дописывать их после ID.

Контракт модели: `stableId: String?`, `projectId: String?`, `title` как чистый пользовательский текст, сохранённые raw-сегменты метаданных. UI показывает название проекта отдельной подписью/чипом. `lineIndex` остаётся подсказкой позиции. Не подменять UUID его `hashCode().toLong()` как гарантированно уникальным ID.

P0 должен распознавать и сохранять project/ID при toggle, rename, schedule, resize, unschedule и копировании на завтра. Из названия скрывать поддерживаемые метаданные и block ID; произвольные квадратные скобки и пользовательские ссылки не вырезать общим regex. Неизвестные поля переносить без потери при редактировании.

Legacy-задачи без ID продолжают работать. Постоянный ID можно добавить при первой реальной правке, а не переписывать все дневники при чтении. Если title совпадает у нескольких legacy-задач после сдвига строк, возвращать неоднозначность и обновлять экран вместо изменения первой строки. Повторяющийся stable ID также запрещает адресную запись до разрешения дубликата.

**Дневная семантика:** создание задачи из проекта пишет только daily. Обратный список действий проекта — результат чтения `[project:: UUID]`, не поддерживаемая копия чекбоксов в проекте. Секция `NEXT_ACTION` («Следующее действие») допустима как текстовая подсказка, но не как второй checkbox или второе состояние выполнения. Кнопка подставляет её текст в форму новой daily-задачи; само сохранение проекта задачи не создаёт и секцию не очищает. Повтор той же команды добавления использует прежний UUID; намеренное создание ещё одного действия — новая команда.

**Копирование на завтра:** сохраняет историческую задачу вчера и создаёт новую дневную попытку с новым task ID и тем же project ID. Для идемпотентности рекомендуется `[carried_from:: <предыдущий task UUID>]`; повторное нажатие для того же источника/дня не создаёт дубль. Не сравнивать только title. Завершение новой попытки не переписывает вчерашнюю историю. Единая глобальная задача со сквозным статусом и настоящим переносом — отдельный P1-контракт.

## 8. Сохранение, внешние изменения и ошибки

Для редактора сущности хранить исходный текст/revision и локальный draft. Перед сохранением перечитать файл. Если он изменился, не отправлять полный устаревший документ поверх: сохранить draft и предложить «Загрузить новую версию». P0 может консервативно отказать при любой смене revision; автоматическое слияние не требуется. Пользователю должен быть доступен текст его черновика для повторного применения.

Патч изменяет только выбранные frontmatter-поля и редактируемые секции. Остальные байты по возможности сохраняются, включая неизвестный YAML, порядок полей, комментарии и секции плагинов. Дубли одинаковых управляемых заголовков или malformed YAML — повод для read-only состояния, не для угадывания места записи.

Mutex обеспечивает последовательность внутри приложения; чтение перед записью не является межустройственным compare-and-swap. SAF не обещает атомарной замены. Сохранение и последующая проверка уменьшают риск, но не дают гарантии отсутствия гонки с Syncthing. Обнаруженный конфликт не лечить автоматическим выбором «более нового» текста. Предусмотреть восстановление предыдущего текста в слое записи до включения редактирования существующих заметок; конкретный механизм — зона основного агента.

| Ситуация | Текст/поведение P0 |
|---|---|
| Vault не подключён | «Подключите папку Obsidian, чтобы сохранять цели и проекты» → «Выбрать папку». Не показывать пустую систему как будто данные прочитаны. |
| Отозваны права / только чтение | «Нет доступа для записи» → «Выбрать папку снова». Черновик остаётся. |
| Первая установка, папок нет | «Начните с проекта или сразу добавьте задачу»; папка создаётся при подтверждении записи. |
| Нет сферы у проекта | «Без сферы» и необязательное «Выбрать сферу», без блокировки действий. |
| Нет задач проекта в открытом дне | «На этот день действий пока нет» → «Добавить действие в план». Не утверждать, что нет задач во всём vault. |
| Нет daily для выбранной даты | Нажатие «Добавить в план» создаёт daily через существующий store. Если создание не удалось, проект не меняется, форма остаётся. |
| Ссылка указывает на отсутствующий ID | «Проект не найден» / «Цель не найдена». Сама задача остаётся доступной; предложить выбрать связь заново. |
| Два файла с одним entity ID | «Найдены две версии записи»; обе доступны для просмотра, адресная запись заблокирована. Не выбирать первый файл. |
| `.sync-conflict` | Исключить из обычного индекса, показать предупреждение у соответствующей записи и доступ к разбору в Obsidian. Не удалять конфликтную копию. |
| Внешняя правка при открытом редакторе | «Запись изменилась в Obsidian. Ваш черновик сохранён» → загрузить свежую версию / скопировать черновик. |
| Запись не удалась | «Не удалось сохранить» → «Повторить». Не закрывать форму и не говорить «Сохранено». |
| Сохранение успешно | «Сохранено в Obsidian» означает локальный файл. Не показывать «Синхронизировано» без состояния Syncthing. |
| Чтение/индексация не завершились | Индикатор и «Обновляю записи…», последний успешный результат помечен как неактуальный. Не мигать нулевыми счётчиками. |
| Пропущена неделя / нет статистики | Предложить обзор сейчас; данные не заменять нулями, не требовать заполнить историю. |

Отмена/архивация сущности не удаляет `.md`, пользовательские ссылки, задачи и размышления. P0 не нуждается в массовом удалении, переименовании папок и миграции существующего vault.

## 9. Разумные значения по умолчанию

- Предлагаемые, но не создаваемые автоматически сферы: «Здоровье», «Работа и деньги», «Отношения», «Развитие», «Дом и быт». Можно сразу написать своё название. Пользовательские существующие направления не заменять этим списком.
- При быстром создании сущности — черновики; активация доступна из деталей после минимального уточнения. Сроки целей и проектов не навязываются.
- У нового действия из проекта дата сегодня, времени нет. Из Плана дата равна выбранной. До сохранения дата видна словами; при открытой через полночь форме не менять её незаметно.
- Сохранить действующий `DEFAULT_TASK_MINUTES = 50` для размещения/фокуса. Не вводить рядом другую скрытую длительность. В форме длительность видна и редактируется; для действия без времени её можно не записывать.
- Одно главное дело дня использует существующий механизм приоритета. Новые статусы целей и недельные акценты не создают второй несовместимый приоритет.
- Пересмотр принятого решения: предлагается через 7 дней, пользователь меняет дату. Даты календарные в локальной зоне; timestamp не используется вместо даты задачи.
- Обзор недели: предлагаемый бюджет 10 минут — подсказка, не таймер и не критерий успешности. Краткий полезный ответ лучше формального объёма.

## 10. Реальные границы кода и приоритеты

### P0 — выпускать только целыми сценариями

| Пакет работ | Изменения основного агента | Граница |
|---|---|---|
| Чтение/запись сущностей | Новый `data/life/` либо отдельный модуль рядом с `data/vault/`: модели, frontmatter/section parser, repository/store; SAF primitives существующего repository | Только пять папок FocusDeck, один файл за операцию, ID-index в памяти как восстанавливаемый кэш. Не Room как второе хранилище истины. |
| Вход и просмотр | Один новый `ui/life/` с общим списком, detail/editor и минимумом ответвлений; Home callback; внутренний маршрут в Root; wiring в существующей точке создания ViewModel | Без новой системы навигации и переписывания остальных четырёх вкладок. |
| Связь задачи | `DailyNote.kt`, `DailyNoteParser.kt`, `VaultDayStore.kt`; поле проекта в форме задачи/переход из проекта | Только основной агент пишет этот участок. Новый life-store вызывает команду daily-store, не пишет daily напрямую. |
| Идентичность и UI title | Чистый title + projectId + stableId; проверить ключи в Planning, Timeline, Home и сопоставление активного фокус-блока | UUID не должен утечь в видимый title или потеряться при rename. Где сохраняется Long-key для жестов, отдельно хранить стабильную идентичность. |
| Решение | Общий editor + draft/adopted/closed, review date, история в теле | Без таблицы весов и автоматических рекомендаций. |
| Обзор | Файл за период, три поля, завершение/черновик | Ссылки на текущие цели/решения достаточно; автоматическую статистику можно отложить. |
| Надёжность | Ошибки доступа, конфликт revision/ID, сохранение draft, повтор операции без дубля | Нельзя сокращать ради декоративных панелей. |

Предлагаемый бюджет **всей четырёхчасовой итерации**, а не обещание точного времени отдельных функций: 0–20 минут контракт и первичный обзор; 20–80 хранение и формат задач; 80–140 общий экран и вертикальный сценарий; 140–170 решения/обзор через тот же editor; 170–210 интеграционные проверки; 210–240 проверки устройства/релиза основным агентом. Ветка работы этого UX-агента заканчивается документом, не включает аппаратное тестирование.

Если безопасная запись занимает дольше, сначала убрать автосводку недели, фильтры/архивный браузер и богатые формы. Решение и обзор могут остаться простыми списками и общим Markdown-section editor. Нельзя выпускать кнопку сохранения, которая теряет чужие секции, или назвать неработающую ссылку на план завершённым сценарием. Не реализованный сценарий отметить в итоговом отчёте явно.

### P1 — после рабочего цикла

- Бессрочный inbox и общий backlog действий; заранее выбрать источник единого статуса, определить миграцию daily-owned задач. Не добавлять master action-файл поверх существующего чекбокса без такого контракта.
- Индекс всех действий проекта по истории daily, фильтры по датам и явный выбор периода. P0 честно ограничивается текущей дневной выборкой.
- Истинный перенос единой задачи между днями с журналом истории вместо копии дневной попытки.
- Количественные метрики целей, этапы проекта, waiting-for/context/energy, повторения и зависимости задач.
- Автоматическая сводка недели с обозначением пропущенных данных; графики только после проверки полезности.
- Тонкое слияние конфликтов по полям, наблюдение за файловой системой, быстрый локальный индекс; браузер конфликтных версий.
- Поддержка пользовательских шаблонов, выбор альтернативной корневой папки, управляемый импорт существующих жизненных заметок.
- Настройка дня обзора, поиска, сортировки, дополнительных связей и архивного браузера.

Не включать в эту сборку: перестройку Obsidian под PARA, новые плагины Obsidian, собственный движок синхронизации, новые корневые вкладки, рейтинги «баланса жизни», AI-переписывание рефлексии, новые обязательные квоты дневника/обзора.

## 11. Критерии приёмки для основного агента

Проверки проводить на фикстурах и отдельном QA-vault; реальный vault не использовать для разрушающих экспериментов. Этот документ сам тесты приложения не запускал.

1. Пустой FocusDeck: создать задачу напрямую; затем создать проект без сферы и цели и добавить связанную задачу. Обе сохраняются, UI не заставляет проходить пять форм.
2. Полная цепочка: область → цель → проект → task; закрытие task меняет один checkbox daily и не завершает проект/цель. ID-связи читаются после перезапуска.
3. Round-trip Markdown: кириллица, двоеточие в title, неизвестные YAML-поля, многострочные секции, плагины и текст вне управляемой части сохраняются.
4. Task round-trip: toggle/rename/schedule/resize/unschedule сохраняют `[project:: UUID]`, block ID и неизвестные метаданные; metadata не попадает в видимый title, block ID остаётся в конце.
5. Одинаковые title у разных проектов и сдвинутые внешним редактором строки: изменяется выбранный stable ID; неоднозначная legacy-задача не меняется.
6. Дважды нажать добавление/перенос: одна запись операции, не два checkbox; копирование на завтра получает новый ID, исходная история и projectId сохраняются.
7. Завтрашняя задача открывается в завтрашнем Плане; Главная остаётся на сегодняшнем дне. Граница полуночи не меняет дату уже подтверждённой операции.
8. Внешняя правка после открытия формы: сохранение не затирает её, draft доступен. Конфликтная копия и duplicate ID не дают ложного второго проекта в обычном списке.
9. Решение: draft → active с причиной/критерием/датой → видимость по наступившей review date → итог пересмотра сохраняет исходное обоснование.
10. Обзор: черновик переживает навигацию/перезапуск; завершённая запись имеет период, повторное открытие не создаёт дубликат. Пропущенные дни не получают фиктивные нули.
11. Ошибки SAF/нет прав/нет daily/невалидный YAML: нет ложного успеха и потери черновика; повтор записи возможен после устранения причины.
12. Существующие тесты дневника/ритуала/таймлайна проходят; новые экраны не изменяют правила обязательного ритуала и доступ к приложениям. Доступность, клавиатура и масштаб шрифта — аппаратная проверка основного агента.

## 12. Короткий handoff

Контракт папок и сущностей принят. Для самого короткого P0 достаточно общего редактора с разными секциями, одного входа с Главной и передачи `projectId` в существующую запись daily-задачи. Сначала обеспечить сохранность metadata и ID при всех текущих операциях, затем украшать карточки. Приоритет продукта — понятный переход от причины к действию и обратно к осмысленному пересмотру, без обязательной предварительной каталогизации всей жизни.


## 13. Переход к UI-реализации

По следующему поручению этот агент реализует только новый `ui/life/LifeScreen.kt` и при необходимости компоненты рядом. Основной агент владеет ViewModel/UiState, репозиторием, Root/Main, сборками и телефоном. Спецификация выше описывает цель; фактически доступные переходы и проверки берутся из актуального API ViewModel. Статус готовности UI сообщается отдельно.
