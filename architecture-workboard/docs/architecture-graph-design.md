# Архитектурная карта: единое полотно

Текущий алгоритм, 21 сентября 2026. Построение автоматическое, без ИИ. Этот документ заменяет прежнюю модель последовательного раскрытия папок.

## Навигация

Первый экран выбирает крупный компонент решения: NotificationService, NotificationAdmin, NotificationHistory и т. п. Это единственный уровень перехода. Внутри компонента все типы находятся на общем полотне. Папки, слои и функциональные области отображаются рамками зон, не страницами. Вложенные классы не требуют отдельного перехода.

При масштабе меньше 30% карточки скрыты, видны зоны с читаемыми экранными подписями и связи между зонами. При приближении карточки появляются на прежних координатах. Масштаб меняет представление, а не данные или раскладку. Нажатие зоны, поиск класса и фокус на соседях только перемещают камеру.

## Факты и зоны

Roslyn/MSBuild предоставляет символы, исходные файлы, проекты, вложенность типов и семантически разрешённые связи. Принадлежность исходникам хранится отдельно от визуального размещения.

1. Верхняя граница определяется семействами проектов, solution folders, Modules, Tests и Shared. Проект не считается автоматически отдельным сервисом.
2. Внутри компонента выделяются явный модуль либо первая значимая физическая папка под слоем. Все её потомки входят в одну зону. Services/src и прочие промежуточные технические папки не создают дополнительные экраны.
3. Если папки не дают сведений, используется namespace. Название зоны дополняется её слоем, поэтому Application / Repositories и Infrastructure / Repositories не выглядят одинаковыми безымянными Services.
4. У каждого типа одна карточка и одна визуальная зона. Отдельно сохранён путь к исходному владельцу.
5. Для сохранения контекста добавляются непосредственно связанные классы других компонентов, сгруппированные по компонентам. Это однопереходное окружение, не рекурсивное включение всего решения. Состав внешнего компонента полностью доступен через его выбор на первом экране.
6. Тестовые и сгенерированные зоны по умолчанию выключены. В меню зон они видны и включаются явно. Скрытие зоны удаляет все её входящие и исходящие линии из отображения, сохраняя геометрию остальных зон.

Группы являются объяснимым структурным представлением, а не доказанными DDD bounded contexts. По одному слову Services или высокой связанности бизнес-модуль не изобретается.

## Контракты рядом с реализациями

Используются только подтверждённые связи реализации/наследования интерфейсов. Через цепочки базовых интерфейсов находятся конкретные реализации; обход защищён от циклов.

Контракт размещается в зоне, содержащей больше всего его известных реализаций. При равенстве предпочитается текущий компонент, затем стабильный идентификатор зоны. Собственный контракт не переносится во внешний компонент. Внутри зоны карточка интерфейса располагается рядом с одной из реализаций, остальные сохраняют настоящие связи с ним.

Карточка остаётся единственным реальным символом, без скрытых дубликатов. В подписи видно исходный слой, в подсказке — весь путь. Вызовы интерфейса всё ещё направлены в интерфейс. Связь «реализует» не превращается в утверждение, какая реализация вызывается во время выполнения. Если реализации находятся в нескольких зонах, часть межзонных пунктирных линий остаётся — это реальное архитектурное отношение, его нельзя удалить ради внешнего вида.

## Геометрия и линии

Зоны упорядочиваются по роли слоя; внешние компоненты размещаются после основного. Детерминированная упаковка использует свободные вертикальные полосы, избегая перекрытий и огромных пустот из-за одной высокой зоны. Внутри зоны не более четырёх колонок; порядок учитывает связи типов и соседство контрактов с реализациями. Высота ряда соответствует самой высокой карточке; между рядами и колонками оставлены коридоры.

На дальнем масштабе отношения объединены по направленным парам зон. На ближнем фоновые отношения объединены по парам типов. Выбранный метод раскрывает точные входящие/исходящие вызовы и порты методов. Внутренние самовызовы класса без выбора не загромождают карту.

Маршрут внутри зоны следует свободным промежуткам. Межзонная линия выходит в коридор, обходит рамки соседних зон и доходит до настоящего целевого класса. Повороты сглажены. Исходные символы, направления и виды отношений остаются в списке связей, независимо от агрегации.

Раскладка и общие межзонные маршруты вычисляются в Worker. Наведение, выделение, масштаб и видимость зон не вызывают повторную раскладку. Включение функций меняет размеры карточек и требует новой раскладки. Изменение состава исходников также может изменить размещение; гарантии минимального перемещения при структурных правках пока нет.

## Проверки и границы

Тесты проверяют полноту единого полотна, отсутствие дубликатов, сохранение целей вызова интерфейсов, работу с базовыми интерфейсами, удаление инцидентных связей скрытой зоны, сохранение исходных отношений при агрегации, неперекрытие карточек/зон и обход карточек маршрутами. Видимость и масштаб не входят во входные данные раскладки.

Неразрешённые зависимости исходного проекта ограничивают полноту карты. Уведомление о диагностике остаётся доступно; отсутствие стрелки при ошибке разрешения не доказывает отсутствие зависимости. Распознавание runtime DI, reflection, внешних сервисов и автоматически доказанных бизнес-контекстов не реализовано. Для интерфейса с реализациями в разных зонах выбирается одно основное место, а не автоматически созданные зеркала карточки.
