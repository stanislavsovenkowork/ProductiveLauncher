# System protection work, 3 November 2026

This is an unfinished research fixture, not a product installer or active network protection. No PF, hosts, DNS, VPN, USB or route changes were made. The existing v5 user agent was not changed by this work.

An explicitly bounded native authorization probe ran the Apple-signed `/usr/bin/id -u` through macOS Authorization Services. Its UI displayed success only for exactly `0\n`, establishing one short root child, not a persistent root service. The operator did not press the probe button or enter credentials. The separate probe process was subsequently stopped and its QA scope closed. The app was opened immediately before its start marker; that short interval is not retroactively marked as QA. The probe source is in `../root-auth-probe/`; `AuthorizationExecuteWithPrivileges` is deprecated and the probe does not establish a safe installation path for arbitrary binaries.

The system's accessible signing identities were empty (`security find-identity -v -p codesigning` returned 0); no provisioning profiles were found in the three standard local profile directories inspected. This does not establish what exists in other locations or developer accounts. A deployable Network Extension needs the appropriate Apple provisioning, Network Extension entitlement, signing identities and compatible system-extension packaging. Its coverage, coexistence with the user's VPN, and operation on this device remain unverified.

The SelfControl 4.x CLI documents start, status and settings, but its public source rejects starting an already active block and intentionally does not provide a normal early stop. The published `master` PacketFilter code invokes `pfctl -E -f /etc/pf.conf -F states` on start, rewrites global PF configuration, and can invoke global `-d` on forced cleanup. We did not establish byte correspondence between that source and the vendor's 4.0.2 binary. An ordinary SelfControl network test was not run because this behavior would risk established VPN/network connections. Its public FAQ also notes VPN and encrypted-DNS limitations, and the project is GPL-3.0.

The official 4.0.2 archive was subsequently downloaded for inspection only; ZIP SHA-256 `15d8fd17839746c608d0c4e929b650d741e691ebee6f893320c783e86ac75926`. The extracted app passed `codesign --verify --deep --strict`, and the CLI passed strict verification; their Developer ID Team ID was `EG6ZYP3AQH`. The signed `org.eyebeam.selfcontrold` executable SHA-256 `7513493b65bc27afa68e5744e075fd9a38c54fae60d0d762365760065ef0852a` contains the same PF command strings described above. String presence is not proof of the exact runtime branch. Nothing was installed or run. A read-only native PF probe was prepared but not opened: recent user input was detected, and the proposed conditional start still lacked a verified restoration guarantee. Even a preflight snapshot of disabled PF and zero states cannot be atomic with SelfControl's later global reload/flush; unrelated rules or state can appear between them, and erased connections cannot be restored by the tested code. The proposed SelfControl test therefore remains blocked, without a claim about the actual live PF state.

Only `com.apple/*` anchor hooks were seen in the on-disk `/etc/pf.conf`. Read-only `pfctl` status and anchor queries returned `/dev/pf: Permission denied`; the live ruleset, enablement and loopback skip remain unknown. No PF mutation was attempted.

After a separate explicit user authorization, the prepared PF Readonly app executed its read-only aggregate check: its UI reported PF disabled, zero current states, 2 rule lines, 2 NAT lines and 1 anchor line. This is a point-in-time aggregate, not proof of the specific live anchor hook or reference list. The operator did not enter credentials or interact with a system authorization dialog. Its own process and `pfctl` processes were absent after cleanup, and scope `9134a106-5352-4d25-a32d-b3caef577a49` was closed. The app was opened before this scope began; only the subsequent diagnostic action was inside the scope. No owned remote VPN test endpoint or independent allowed control was available, so no packet-filter modification or network QA followed.

`StrictRootStore.swift`, `StrictRootAuthority.swift` and `StrictAppEnforcer.swift` are reviewable local building blocks, tested with temporary files, synthetic models and mocked signals. Their tests do not prove a root daemon, durable recovery after power loss, or application enforcement. `StrictFixtureDaemon.swift` is a **single-window, synthetic-target-only unfinished fixture source**; it is not installed, and its latest revision was not compiled or tested as root. A future installer must have a reviewed native bootstrap, independent bounded stop/recovery, exact ownership and cleanup verification, and an explicit authorized user action. The root directory, helper directory and socket paths for this fixture were absent at the final read-only check.

`HostsQA.swift` transforms temporary bytes for one generated `.invalid` QA name, and `test-hosts-qa.sh` covers its own marker, conflict refusal and byte-preserving expected-state transitions. It is not a root file writer. Normal read-then-rename does not give an atomic compare-and-swap against unrelated writers: an external edit between recheck and rename can be lost. Advisory locks cannot guarantee cooperation from other applications. Until that conflict and an independently verified recovery are addressed, no `/private/etc/hosts` operation is reviewable under the requirement to preserve concurrent changes. Even a correctly installed exact-name hosts rule would only cover qualifying system resolver use and would not prove universal browser, DoH, direct-IP, ECH, cache or existing-connection enforcement.

The proposed fallback of exact hosts entries for Safari/Chrome plus terminating explicitly selected unsupported browsers is **NO-GO for the requested broad protection**. An exact root-domain entry does not cover ordinary subdomains, and the application enforcer can target only an explicit trusted signing-ID set, not an unknown additional browser. Existing connections, caches, direct IP and Safari Private Relay are not proven covered. Chromium does have HOSTS lookup paths, including in configurations with its built-in DNS resolver; saying that all Chrome DoH necessarily ignores hosts would also be unsubstantiated. Neither supported browser's real behavior nor the root app enforcer has been accepted on this machine. A limited resolver-specific feature remains possible after a safe writer/recovery and isolated end-to-end testing; it is not a universal browser barrier.

## LuLu 4.5.7 feasibility

**NO-GO for the required controlled protection.** LuLu documents selecting a local block list, reloading changed files, and giving the block list precedence over allow lists and application rules. Its documented profile selector changes which profile is active; a new profile starts without the chosen list. No documented mechanism was found to lock that profile or acknowledge application of a FocusDeck-owned list for the duration of a window. In the tagged provider source, disabled filtering permits new flows before block-list evaluation. Consequently a root-owned list alone does not establish protection against ordinary UI changes, and a safe managed install/test/cleanup path satisfying that requirement has not been demonstrated.

The vendor documents Chrome filtering by IP rather than hostname; hostname availability for Safari and Firefox depends on the flow. Direct-IP filtering may affect unrelated services sharing an address, and existing connections were not tested. Compatibility with this Mac's VPN and preservation of its existing connections remain unverified. LuLu was not installed or run, and no settings or network state were changed for this assessment.
