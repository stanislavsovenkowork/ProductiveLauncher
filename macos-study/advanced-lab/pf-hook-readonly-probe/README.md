# PF wildcard hook read-only probe

The probe calls the Apple-signed `/sbin/pfctl` with `-s info`, `-s rules`, `-s nat` and `-s Anchors` using Authorization Services. It reports only aggregate counts and whether the main rules output contains the exact unconditional `anchor "com.apple/*"` form. It does not print or persist the rules or connection addresses, and it does not modify PF. Empty output or failed parsing is unknown, not evidence that rules are absent. `AuthorizationExecuteWithPrivileges` does not give this probe a reliable exit status for each child, so its displayed counts and hook detection are informational only.

On 3 November 2026, after explicit authorization of this specific read-only operation, the UI reported PF disabled, zero current states, two filter-rule lines, two NAT lines, one anchor line, and the unconditional Apple wildcard hook present. The dedicated scope `3c6ed45c-cf19-407f-b276-43d7b038110b` opened before launching the app and closed after its process and `pfctl` were absent. No password or system-dialog input was entered by the operator. No PF or network mutation was performed.

The Apple hook is not a separately owned hook. This check did not inspect nested rule effects, enable references or concurrent changes. Reading rules and then enabling PF are separate operations; no verified atomic preflight-and-enable mechanism prevents a system service, VPN or other writer from changing the rules in between. Thus this result alone cannot establish that global enablement leaves unrelated connections unaffected or that a later `-X` can undo any connection effects. The CERN public test endpoint discussed for a possible future probe is not owned by this project; a rule limited only by IP and user ID could still affect another process. No proposed QA mutation was run.

The installed `pfctl` binary contains a `Token : %llu` format and displays PID, process name, token and timestamp for enable references. An independent supervisor started before enabling might attempt crash recovery by comparing a baseline and a uniquely identified enabler, releasing only an unambiguous token. This is a design possibility, not a tested recovery: root-owned staging, a launcher, reference parsing and interruption handling were not implemented or verified. No guarded mutation script was produced, no enable reference was acquired, and no PF rules were changed.
