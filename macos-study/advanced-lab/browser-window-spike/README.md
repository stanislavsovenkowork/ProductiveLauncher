# Browser/window spike — 2026-11-02

**Decision: no-go for connecting the legacy browser worker to the candidate as-is.** This isolated spike tests a decision model, not browser enforcement. No app, browser, network, permission, personal tab, vault or service was changed.

`SpikeTests.swift` combines the existing V2 policy transition core and the legacy URL matching on synthetic inputs. It checks active, bounded relief, automatic relief expiry, return, pending exit, full exit, unavailable reply and host boundaries. The simulated reply is not a real authenticated status, and the simple fixture is not a production gate. Run from the repository root:

```sh
xcrun swiftc -swift-version 6 macos-study/Sources/WindowPolicy.swift macos-study/Sources/WindowGuardV2.swift macos-study/advanced-lab/Sources/StudyPolicy.swift macos-study/advanced-lab/Sources/BrowserControl.swift macos-study/advanced-lab/browser-window-spike/SpikeTests.swift -framework AppKit -o /tmp/focusdeck-browser-window-spike-test
/tmp/focusdeck-browser-window-spike-test
```

The old `BrowserCoordinator` is driven by the archived prototype UI, with its own 25-minute deadline and pause extension; closing that UI ends its polling. It does not follow the current independent calendar agent. The worker enumerates tabs in already-running Safari, Chrome and Opera GX, reads URLs in memory and changes a matched URL to `about:blank`. This can interrupt page state and is not a verified privacy-safe test on personal tabs. AppleEvents permissions, browser dictionaries, private windows, unlisted browsers, other traffic, start timing and actual effect are not established. Polling is bypassable and does not prevent a page loading between polls. `selected_apps_requested` reports an app request, not site coverage.

A useful next increment needs an explicitly chosen and persisted domain policy, an independent user-session lifecycle bound to the calendar authority, a fresh trustworthy state (including clock uncertainty), cancellation/revalidation of in-flight actions on relief/exit, a clear Automation-permission and incomplete-coverage status, and a reversible isolated browser fixture. In particular an old or unavailable response cannot be presented as verified protection. Existing status messages and a synthetic state transition do not prove action. Investigate an approach that preserves return context before changing any real tab. Verify actual browser behavior, reboot/sleep, race conditions and VPN/GitLab/Codex compatibility in the agreed scope before enabling it for a user. No root, MITM, SIP changes or personal tabs are needed for the present spike.

## Integration decision after inspecting the current user agent

The candidate build does not include `BrowserCoordinator`, `BrowserWorker`, or `BrowserControl`; those belong to the archived prototype. `UserProtectionLedger` stores app signing requirements and window/schedule state, with no selected-domain policy. The current agent loop scans processes and handles requests; it does not own an AppleEvents worker. A UI-only poller cannot cover the promised window after the app closes, and the old poller has an unrelated 25-minute deadline. Thus simply calling it from `syncCandidate()` would produce an independent, misleading second authority.

The immediate blocker is not domain matching: it is the **lifecycle and action boundary**. A browser command already dispatched asynchronously may still replace a tab after relief or exit is committed; killing a worker does not prove an already-sent AppleEvent was cancelled. The reverse problem also exists when the UI is closed or a worker/Automation permission fails: a saved policy is not evidence of enforcement. A deployable implementation must define and test how the authority serializes or drains pending browser actions against transitions, report uncertainty honestly if it cannot confirm cancellation, and preserve context. The agent also needs a user-selected, validated, persisted domain list with explicit scope and protected infrastructure exceptions, plus an independently running user-session worker and Automation authorization. This is a substantial coordinated feature, not a safe isolated glue change.

The present code cannot safely demonstrate it on a synthetic URL inside an ordinary browser: its scan enumerates every tab of each supported running browser, so an isolated test needs a genuinely isolated browser instance or a dedicated scriptable fake endpoint first. Model tests in this directory do not issue AppleEvents. No domain list, browser access, or background service was deployed. The separate Mac QA agent registration failure (`OS_REASON_CODESIGNING`) is an additional unverified delivery blocker; its root cause is unknown and it is not evidence about website blocking.
