# V2 selected-app guard: uninstalled source candidate

This candidate is built separately by `./macos-study/build-v2-production-candidate.sh`. It is **not installed, run as root, or verified against real user apps**. The app contains a candidate-socket client, but no live helper is connected. The script tests core policy decisions with fake peers and synthetic signing IDs only. Do not treat it as deployed protection or as evidence of personal productivity.

The candidate accepts only an authenticated peer (the configured UID plus signed UI CDHash) and a root-owned trust file containing the exact explicitly selected signing IDs, Team IDs and designated requirements captured from verified user-selected applications. Ad-hoc targets or missing Team IDs are rejected. The daemon verifies the process code signature against its pinned designated requirement and Team ID immediately before each signal. A policy snapshot cannot change its targets, absolute end, grant ceiling, or cooling-off delay while the window is active; spent relief cannot be restored. A candidate window must start at or after 15:00 Europe/Minsk, start and end on the same Minsk date, and last at most nine hours. Grant and exit-delay bounds are enforced. The target list has no wildcards; protected IDs include Apple/system, OpenAI, VPN/tunnel, GitLab and Codex identifiers. The fixed protected prefixes are `hossin.asaadi.v2box`, `com.openai.`, `com.v2box.`, `com.hossinasaadi.v2box`, `net.openvpn.`, `org.openvpn.`, `com.tunnelblick.`, `net.tunnelblick.`, and `com.apple.`; additionally the lowercase signing ID must not contain `vpn`, `tunnel`, `wireguard`, `tailscale`, `zerotier`, `globalprotect`, `fortinet`, `cisco`, `gitlab`, or `codex`. The daemon repeats these checks; an active saved target set differing from the loaded root trust aborts startup. Trust is loaded once per daemon run and cannot be changed through the socket. These conservative name checks are not a complete inventory of every corporate dependency: check selected apps and their dependencies before any future live use.

The candidate only scans the target user's processes, rechecks the process identity and signature immediately before a signal, and refuses protected IDs. It first sends SIGTERM, then SIGKILL after two seconds if a selected process remains. **This can discard unsaved data.** A selected browser is targeted as an entire application; actual coverage of its processes has not been verified. It does not filter sites, DNS, encrypted DNS, other browsers, browser processes with mismatched signing IDs, or non-app executables missed by the scanner. Apple apps including Safari are excluded by the conservative protection rule. The daemon never changes hosts, networking, VPN, SIP or certificates.

The independent daemon can continue an already accepted window after the app quits, provided the daemon remains running. Its root-owned snapshot carries the window and same-boot monotonic expiry and relief bounds across daemon restart. This has not been tested as a real privileged service, including sleep, daemon crash or reboot. After reboot monotonic bounds are reconstructed from wall time; moving the wall clock forward can prematurely reach the absolute end, and clock tampering across reboot is not reliably detectable. No claim of uninterrupted protection is warranted. Future recurring windows are not automatically published; recurring scheduling remains an open requirement.

The service is source code and a standalone binary only. There is no tested root installation or launchd job for it, no device-verified production UI selection or app-to-daemon status, and no verified site protection. The separate `V2-FIXTURE-QA.md` administrator package is permanently constrained to the synthetic fixture and must not be repurposed as a production installer. Recovery and opt-in weekly review remain independent from enforcement.

Before any future activation, the UI must display the exact chosen signing IDs and corresponding apps, explain that termination can lose unsaved work and that a browser is blocked in full, and offer the configured limited relief and deliberate full exit. Only an explicit user choice may publish a policy; there are no personal targets selected by default. This complete production consent and control path is **not yet implemented**.

## Independent emergency recovery candidate

The separate `FocusDeckV2CandidateRecover` binary does not depend on the UI's CDHash. Its explicit root-only `--recover` operation sends a command only to the candidate socket. The running candidate verifies the caller's root UID, durably records a terminal tombstone retaining the consumed budget, acknowledges and stops itself. If the daemon is not reachable, the tool takes the candidate's exclusive lock, checks the ready marker, root-owned configuration, trust digest and approved window against the ledger, and records the same tombstone. It refuses if the lock is held, the ledger or binding is missing/corrupt, or ownership is unexpected. This does not affect the fixture, v1 helper, other services, or any networking.

This is source-level and fake-peer authorization coverage only; neither online nor offline recovery has been tested as root or on a real device. The separate administrator candidate can prepare root-owned placement, but it has not been run under root or verified on a device, and an automatic restart service is not configured. A future installer must install and verify a root-owned recovery binary alongside the daemon, provide a clear user-accessible recovery path, test online/offline recovery and UI upgrade while a window is active, and ensure no service automatically recreates the policy after recovery. Until those steps pass, the candidate is **not suitable for installation against personal targets**.

## Reviewable administrator candidate (not run)

`production-candidate-admin.py` offers `plan`, `install-idle`, `run`, `recover`, and `remove`. The plan rechecks the proposal's UID, UI CDHash, exact application paths, signing IDs, valid signatures, nonempty Team IDs and designated requirements, protected exclusions, and independently supplied SHA-256 values for the proposal and both executables. `install-idle` repeats those checks and refuses any pre-existing candidate directory or socket. It prepares the selected inactive first-window ledger and trust together in a private staging directory, fsyncs files and directories, uses an exclusive directory rename, and writes the ready marker last; it does not start the daemon. `run` is foreground-only and requires the ready marker and the same trust-bound ledger; a terminal window or existing socket is refused. `recover` uses the separate root-only tool, without the UI CDHash, to preserve a terminal ledger and stop its daemon. `remove` refuses an active policy, socket, lock, unexpected file or ownership, and retains the ledger, trust and event log; intentional deletion and reinstallation by a root owner remains an explicit administrative bypass. It does not touch the fixture, v1 guard, other apps, hosts, VPN, or certificates.

For a future user-approved review, after selecting actual applications in the UI, use the proposal created at `~/Library/Application Support/FocusDeckStudy/candidate-trust-proposal.json`. Capture its SHA-256 for review and pass that exact hash again to install; changing the proposal causes refusal. The current build's expected executable hashes are:

- independent recovery: `96886c73769c5c18bcc7d9713b6c885358ed285dee1ccf2167a21e0c096414f8`

No personal target is safe to enable on the basis of this document alone.

## Recurring ledger prototype — not connected

`test-recurring-ledger.sh` exercises a separate in-memory/fake-clock and temporary-file prototype. The prototype binds a schedule to a trust digest, derives a stable revision/date ID, persists one snapshot before returning a decision, keeps the spent daily budget and terminal exit on repeated evaluation, rejects target changes and protected IDs, and stops issuing windows when wall/uptime diverge, a boot changes, or storage is invalid. Its isolated tests cover duplicate evaluation, restart, schedule replacement, next day, clock/reboot uncertainty, corrupt input, and a write failure before replacement. This is not a working background schedule: the prototype is **not wired** into the app, socket, daemon or administrator, and it has not survived injected crashes at every write/rename/fsync boundary or a real reboot. Its storage requires a single external lock; a failure after rename but before directory fsync leaves the outcome uncertain and requires status reconciliation, not a retry that grants additional budget.

The release-blocking integration work is substantial: the privileged helper must become the authoritative owner of schedule, current window, daily ledger, grant and exit; its authenticated status must let the UI adopt the same window and consumed budget rather than creating another UUID; helper commands must durably commit before replying, with stable request IDs and idempotent recovery; UI offline state must say unknown rather than claiming release; user-confirmed schedule changes and the independent root recovery must preserve the same day's ledger. Clock/boot uncertainty needs a deliberate bounded recovery path. Only after crash-boundary tests and separate synthetic privileged device QA can background recurrence be claimed.

## Authenticated status and helper-owned changes

The candidate protocol now returns its current policy snapshot only to the authenticated UI. The UI adopts the helper's window ID and remaining budget when the revision, targets and calendar boundaries match. Relief, return and exit requests first read helper status; the UI changes the cached state only after an accepted helper response. If the connection drops after the helper commits, the UI shows an unknown connection and the next status read adopts the committed state rather than issuing another grant. Conflicting revisions, an empty helper or an unavailable helper do not cause an automatic publish or a restored budget. First enrollment is instead prepared in the root-owned ledger by explicit `install-idle`; automatic daily recurrence remains unavailable.

Before acknowledging an update, the candidate writes a private temporary snapshot, syncs it, renames it and syncs the containing directory. If a sync fails, the daemon does not acknowledge the change; a failure after rename is an uncertain outcome requiring a fresh authenticated status, not an assumed rollback. Synthetic tests cover differing IDs and spent budgets, a committed update with a lost reply, explicit refusal, model restart, empty/conflicting status, and no automatic retry/publish. These tests do not prove actual root filesystem durability, every crash boundary, sleep/reboot behaviour or real enforcement. A lost response can also leave a local event missing, so the event journal remains incomplete rather than evidence of complete history. The frame is bounded to 4096 bytes; unusually large target sets can fail with unknown status rather than being silently truncated.

## Prepared first window and incomplete-install handling

The explicit `install-idle` candidate now records the exact approved inactive first window, its original budget, ID and revision in the root-owned ledger before marking the installation ready. The daemon requires both the ready marker and a ledger matching the immutable trust and approved window. Missing, corrupt, old-format or changed files are errors; there is no silent migration or creation of a fresh budget. The UI sends authenticated status, adopts the saved window and budget, and does not publish a replacement when the helper is empty. After recovery the terminal ledger remains; admin removal preserves it and prevents an ordinary fresh installation in the same directory. A root owner can deliberately remove those files and reinstall: that is an administrator bypass, not protection from the owner.

`test-candidate-enrollment.sh` exercises temporary-file and fake-socket scenarios: first prepared ledger, missing/tampered marker or ledger, incomplete installation before ready, exclusive no-overwrite, unsupported directory fsync, a grant committed with lost acknowledgement, restart/status, duplicate request, and a terminal tombstone across restart. The test uses mocked signing identities and a synthetic service; it does not start the actual privileged daemon, install a root service, validate real Team IDs, inject actual power loss, or prove durability on this Mac. After an ambiguous filesystem or reply failure the UI must report unknown and reconcile status. The recurrence prototype remains disconnected, and no future window is scheduled by a closed app.

## Minimum path to root-authoritative recurrence

Recurrence remains OFF. The current root ledger deliberately binds one approved window ID and its exact dates; the UI also rejects a status for a different local date. `test-recurring-integration-gate.sh` verifies that the present binding rejects the next day and that a terminal same-day window cannot be reset. Enabling only the root scheduler would therefore create a window the UI cannot safely adopt.

A future integrated design must put the explicitly approved schedule, its revision, fixed target trust, each issued local date and its remaining relief/terminal state in the same root-authoritative durable ledger. The helper must create at most one stable window per revision/date after 15:00 Minsk, preserve same-day spending and terminal exit across restarts and rule edits, and fsync the ledger before responding or enforcing. Authenticated status must return that actual window; the UI must validate it against the approved schedule and adopt the root ID and budget without locally creating or replenishing a second window. Lost acknowledgements require status reconciliation and idempotent commands. The separate prototype above is not this integration.

After a boot change or a detected wall/monotonic discrepancy, the helper needs an explicit `clock_unknown` state and must not silently create or extend windows from an unverified wall clock; the UI must show uncertainty, and an independent bounded administrator recovery must remain available. The current daemon instead reconstructs its cap from wall time on a new boot, so it does **not** meet that requirement. Sleep, clock adjustment and actual crash/power-loss boundaries need controlled testing before use.

A crash may also leave a socket path behind. The current administrator refuses to run while a socket exists; it does not claim automatic restart. Any future cleanup must first hold the candidate's exclusive lock, verify root ownership, verify the peer PID and exact candidate executable if a peer exists, and recheck the socket inode before unlinking. A root-owned but unprovable stale socket alone is not proof of ownership: refuse and require explicit inspection rather than removing an unrelated socket. No automatic service or launchd job is part of the current candidate.

The candidate daemon now refuses any pre-existing socket, including a root-owned one, and its deferred cleanup unlinks only the socket device/inode it actually created. This avoids the previous unsafe assumption that root ownership alone proved a stale socket belonged to the candidate. A stale path therefore remains a manual-inspection/recovery blocker; no live root restart has been tested.
