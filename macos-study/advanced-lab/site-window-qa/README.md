# Синтетический Chrome QA: визуальный барьер сайтов

Это только лабораторная проверка, **не установленная защита сайтов**. MV3 content script ограничен `localhost`, а отдельная loopback-страница на `127.0.0.1` играет роль разрешённого материала. Состояние берётся у реального user-agent в отдельном временном каталоге: QA-клиент на каждом соединении проверяет UID и CDHash процесса сервера, а затем запрашивает его состояние. HTTP-мост тестового сценария привязан к `127.0.0.1`, принимает только случайный тестовый capability-заголовок, отказывает несовпадающему `Origin` и выдаёт только фазу; содержимое страниц и URL не передаются агенту. Это не production-механизм доверия к расширению или настройки доменов.

Барьер на уже открытой странице сохраняет её URL и DOM. Он появляется при активном окне, снимается при послаблении/полном выходе/неизвестной связи и возвращается после явного возврата или окончания послабления. Если скрипт или расширение перестанет работать, CSS убирает барьер после пяти секунд без свежего подтверждения. Он **не блокирует сеть или скрипты страницы**, может быть удалён самой страницей и не защищает другие браузеры, профили, неизвестные вкладки, отключённое расширение или другие способы доступа. Страница может загрузиться и выполнять работу до появления барьера. `?` на значке сообщает о неустановленной связи, если worker получает запросы от тестовой страницы; после полного отключения расширения такой индикации нет.

`run.sh` собирает отдельный подписанный ad-hoc synthetic user-agent и клиент в новый `/tmp/focusdeck-site-qa.*`, запускает локальный HTTP-сервер и Chrome в отдельном headless профиле, загружая распакованное расширение через CDP только в этом профиле. Нужны локальные Chrome, Xcode command line tools и Playwright Core; путь к последнему можно указать в `FOCUSDECK_PLAYWRIGHT_CORE`. Сценарий не меняет системный DNS, VPN, маршруты, личный профиль или вкладки и завершает собственные процессы. Он использует `--enable-unsafe-extension-debugging` только для временного процесса; `Browser.getBrowserCommandLine` подтверждает путь профиля и отсутствие `--disable-extensions`. Временные файлы сохраняются в напечатанном каталоге.

2 ноября 2026 проверено на реальном Chrome в отдельном headless-профиле: уже открытая выбранная страница проходит active → relief → return → окончание relief → exit; SPA-смена адреса, потеря и возврат агента, остановка JavaScript и удаление расширения; другой loopback host и контекст страницы не изменены; запрос к мосту без capability отклонён. Проверка касается синтетического агента и визуального барьера, а не производственной установки или доказанной пользы продукта. Первые прогоны не были отмечены в локальном журнале QA, поэтому совпадающие персональные наблюдения могут быть загрязнены; часть последнего прогона отмечена только с момента фактического открытия scope.

Перед пользовательским включением нужны отдельные реализованные и проверенные: явный выбор и хранение точных доменов в авторитетной политике с миграцией без сброса бюджета; доверенный установленный источник состояния и безопасный способ связи с расширением; установка, видимый статус и отзыв; восстановление после сбоев и ограничения частных окон/нескольких профилей; настоящая UI-проверка препятствия обычному взаимодействию. Нельзя представлять этот прототип как системную или сетевую блокировку.

Официальные источники: [Chrome extension service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle), [Chrome extension end-to-end testing](https://developer.chrome.com/docs/extensions/how-to/test/end-to-end-testing), [Chromium CDP loadUnpacked implementation](https://chromium.googlesource.com/chromium/src.git/+/225b2eaa7f23c33b7c4e30c1bfc58f1bd99cbe1c%5E%21/).
