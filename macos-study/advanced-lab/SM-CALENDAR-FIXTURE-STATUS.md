# SM calendar fixture: signing and device status

The fixture is **not deployed**. The operator unregistered the service after macOS refused its launch; launchd job, daemon, synthetic child, fixture root directory and socket were confirmed absent. No test window was created in the refused attempt.

The device log for the 2026-10-29 attempt reports `AppleMobileFileIntegrityError -423` for an ad-hoc/unknown-chain signature followed by enforcing launchd spawn constraint mismatch `c[5]p[1]m[1]e[0]` and `OS_REASON_CODESIGNING`. The failing app and daemon have ad-hoc signatures and no Team ID; `codesign --verify --deep --strict` succeeds on disk but does not establish that macOS will launch the daemon. Another ad-hoc fixture and an earlier version of this fixture previously launched, so a blanket statement that macOS always rejects ad-hoc is unsupported. The log does not disclose the complete generated constraint or establish why it changed.

The machine reported zero valid signing identities via `security find-identity -v -p codesigning`. Apple recommends signing the app and daemon with the same code-signing identity and unregistering/re-registering the service after the daemon executable changes. A valid Apple Development or Developer ID identity would permit that supported signing route, but success on this machine remains unverified and obtaining an identity is outside this change. Do not disable AMFI/SIP, alter system signing metadata, or repeat variants as a substitute for a verified cause.

Current source implements fixture-only service control, one synthetic signed child, bounded window, relief, return, exit and narrow cleanup. Its model-to-helper fake integration, relative argv[0] regression, restart/budget, cleanup refusal, and receiver/report isolation tests passed without root. The corrected helper did not launch in the most recent root test, so those local results do not establish end-to-end device operation, recurring scheduling, personal-app protection or site filtering. The earlier actual root run reached a helper but failed when the helper resolved launchd's relative argv[0]; the synthetic test data was subsequently cleaned up.

References: [Apple launch constraint diagnostics](https://developer.apple.com/documentation/security/applying-launch-environment-and-library-constraints), [Apple DTS signing guidance](https://developer.apple.com/forums/thread/799933), [Apple DTS re-registration guidance](https://developer.apple.com/forums/thread/783539).
